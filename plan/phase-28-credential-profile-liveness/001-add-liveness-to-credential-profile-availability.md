## Purpose and scope

This task closes project followup 0D1g (from mod-repos finding rJGk; user decision 2026-11-03: fix in mod-users now, within the identity-model-impl plan, before mod-core phase 5). The SQL function `mod_users.credential_profile_availability(p_credential_id, p_profile_id)` ignores `credentials.revoked_at` and `credentials.expires_at`. A credential revoked or expired between SSH key resolution and profile derivation therefore still authorizes fetch and push, because `SSHKeyResolver.available` (`api/internal/service/ssh_key_resolver.go`) trusts the function's `'available'` result alone.

Current state, read from `model/migrations/sql/0100_baseline.sql` (line numbers are as of this writing; re-read before editing):

- `credential_profile_availability` is a `LANGUAGE sql STABLE SECURITY INVOKER` function, not a view. Its header comment is lines 1644-1646, `CREATE FUNCTION` is line 1648, and the body (lines 1655-1666) selects `profile_availability_for(c.principal_id, NULL, ARRAY[c.id], k.base_acr, p_profile_id, false)` from `credentials c JOIN credential_kinds k WHERE c.id = p_credential_id`, with `COALESCE(..., 'not_held')` for an unknown credential. It never reads `c.revoked_at` or `c.expires_at`.
- `credential_liveness` (comment from line 2022, `CREATE FUNCTION` line 2028) does check them: unknown credential or `revoked_at IS NOT NULL` gives `credential_revoked` (lines 2054-2056 and 2066-2067), `expires_at <= now()` gives `credential_expired` (lines 2068-2069), and only then it calls `credential_profile_availability` (line 2075). So the client-credentials per-request path is already safe; the SSH resolver, which calls `credential_profile_availability` directly (the `CredentialProfileAvailability` query in `model/queries/sessions.sql`, line 189), is not. `api/internal/service/session_views.go` (around line 114) also calls it for client-credential profile listings.
- The baseline is edited in place (user's earlier decision): no new migration file. `model/migrations/sql/` keeps only `0100_baseline.sql`.

The work targets the plan branch plan/identity-model-impl and lands through the ordinary per-task loop. Scope is limited to this fix; the mod-repos regression scenario is a separate change (see Assumptions).

## Assumptions

- Security-sensitive: this is an authorization bypass (a dead credential still authorizes). Tier sonnet-high.
- The transaction clock (`now()`) is the expiry reference, as in `credential_liveness`. A revocation committed after the function's snapshot but before the caller acts is the caller's concern; the guarantee here is that every call evaluates liveness at call time and never returns `'available'` for a credential that is already dead.
- The downstream consumer is mod-repos `api/transport/sshprofilederivation`, which will add a regression scenario using its existing `setAfterSessionCredential` hook (revoke the credential after session resolution, before derivation). That is a separate mod-repos change and is not part of this task; do not edit mod-repos here.
- The lock-reason strings `credential_revoked` and `credential_expired` are chosen to match `credential_liveness`. If a consumer's mapping makes a different string clearly better, halt and report rather than diverging silently.
