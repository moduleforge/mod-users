## Planned changes

The HTTP clients are `@moduleforge/users-gui`, the app GUIs and servers that compose mod-users, and external clients of `/v1/auth/*`.

1. **401 before 400 on direct mounts (D1).** An unauthenticated request with a malformed body or UUID on an authenticated route gets 401 with code `unauthenticated`. Composed apps already run mod-users' `requireAuth` first, so production clients keep seeing 401 `unauthorized` there. The new behavior only shows on direct mounts and in tests.
2. **User accounts mask misses (D2).** A missing account on `GET`/`PUT`/`DELETE /user-accounts/{uuid}` and `POST .../assume` gives 403 to every caller, admins included. It was 404. `POST .../assume` with no actor on the context gives 401 (was 404). The ssh-key operator routes keep their masked 403.
3. **Stricter decoding everywhere (D6, D7).**
   - Unknown JSON fields are rejected with 400 on every body route, including the public `/v1/auth/*` routes. They were silently ignored.
   - Trailing data after the JSON value is rejected.
   - Bodies over 1 MiB get 400 with detail `body_too_large`; the ssh-key register cap stays at 32 KiB, now with `body_too_large`.
   - Decode and path-UUID 400s gain `details` (`invalid_json_body`, `invalid_uuid`, field errors). The top-level code stays `invalid_input`.
   - Literal "invalid JSON body" messages become apiresp's fixed message.
4. **`POST /user-accounts` (D4).** A malformed body, or missing email, given_name or family_name, or a short password, now gives 400 to any authenticated caller. Before, a caller without create permission got 403.
5. **`PUT /user-accounts/{uuid}` (D4).** A present-but-blank `email`, `given_name` or `family_name` gives 400 (was stored). A duplicate email gives 409 `users.email_taken` (was 500; planned, task 4.1).
6. **`PUT /self` (D5).** A present-but-blank `given_name` or `family_name` gives 400 with `natural_persons.given_name_required` or `natural_persons.family_name_required` (was stored blank). App GUIs pairing mod-core's `ProfileEditor` with this route should show the inline error.
7. **Apps membership (D3).** A bad path UUID, malformed body or missing or invalid `user_uuid` gives 400 before the 403. A non-admin with a bad request now sees 400, where before they saw 403. An unknown app for an authorized admin stays 404. `AllowNotFound("app")` is no longer set on the shared entity resolver. Anything else that uses plain `Resolve` with slug `app` on that resolver gets 403 instead of 404, which matches mod-core alone. A body `user_uuid` that names no account gives 422 (was 404; planned, task 4.1). `gui/src/lib/api.ts` `apps.addMember` sending `role` would be rejected as an unknown field; task 5.1 aligns it to `roles`.
8. **Step-up after shape checks (D9).** On the identities and ssh-key credential routes, a malformed body or UUID gives 400 even when no step-up token is present (was 409 `users.step_up_required`). A malformed request no longer consumes a step-up token.
9. **SSH key parsing before authorization (D10).** A malformed `public_key` or label gives 400 to a caller who may not update the account (was 403).
10. **OIDC config (D7, D8).**
    - Admin-bearer or `X-Setup-Token` callers with a malformed body get 400 after authentication. Body-token callers with a malformed body still get 400 first, a documented exception.
    - Provider bodies are capped at 1 MiB, unknown keys are rejected, and trailing data is rejected.
    - The 409 on an existing provider id keeps its status and code and gains detail `users.oidc_provider_exists`.
11. **Public auth literals (D12).**
    - 500 `internal_error` messages become generic.
    - Required-field 400s keep their status and code and may gain field details (new detail codes are listed by task 3.7).
    - `GET /auth/oidc/{provider}/start` no longer echoes the internal error text in its 400 message.
    - Credential-failure 401 messages and the middleware's `unauthorized` 401s are unchanged.

In-process callers:

12. `UserAccountService.Get`/`Update`/`Delete`/`Assume` return `ErrForbidden` on a miss (was `ErrNotFound`). `Assume` with no actor returns `ErrUnauthenticated`.
13. Consumer authorizers (mod-users `Authorizer`, test fakes) receive an extra `Authorize` call with target `0` on each masked miss. It must be denied quietly (common rule 5), and audit logs show one such call per masked miss.

## Recorded by tasks

Tasks append dated entries here: route, old behavior, new behavior, and the client that may notice.

- 2026-10-11, mount-require-auth (1.2): the 8 authenticated registrars (`RegisterAccountRoutes`, `RegisterSelfGetRoute`, `RegisterSelfPutRoute`, `RegisterSelfIdentitiesReadRoute`, `RegisterSelfIdentitiesWriteRoutes`, `RegisterSelfSSHKeysReadRoute`, `RegisterSelfSSHKeysWriteRoutes`, `RegisterUserAccountSSHKeyRoutes`) now mount mod-core `authz.RequireAuth` inside an `r.Group`. Old: 401 depended on the composer mounting a token-verifying `requireAuth`; a direct mount with no actor reached the handler (and a malformed body or UUID got 400). New: a request with no effective actor gets 401 code `unauthenticated` before any handler code. Production is unchanged (the module's `requireAuth` runs first and answers 401 code `unauthorized`); only direct mounts and tests, such as `app-mfmanager` `svcconfine_integration_test.go`, can notice. A sudo-only identity passes the gate.
- 2026-10-11, user-account-masked-miss (2.1), planned items 2, 12 and 13: `GET`/`PUT`/`DELETE /v1/user-accounts/{uuid}` and `POST /v1/user-accounts/{uuid}/assume` now return 403 (`forbidden`, identical envelope) for a UUID that names no account, for every caller, admins included. Old: 404 `not_found`. `UserAccountService.Get`/`Update`/`Delete`/`Assume` return `apiresp.ErrForbidden` on a miss (was `coreservice.ErrNotFound`); `Assume` with no effective actor returns `apiresp.ErrUnauthenticated` (was `ErrNotFound`, so 404). `Assume` now reads the sudo-aware effective actor (`opctx.EffectiveActorEntityID`) for the admin lookup, so a sudo-only identity is no longer rejected there, and the admin account lookup runs after authorization. The ssh-key routes (`SSHKeyService.loadAuthorizedAccount`) share the same helper: a missing account or missing account-holder entity is a masked 403 as before, and a key miss on revoke stays a masked 403 for every caller. Side effects: the ssh-key service now requires an authenticated context (`ErrUnauthenticated` otherwise), and it authorizes before the archived-holder check (an archived holder still gives 403). Consumer authorizers receive one extra `Authorize(op, &0)` call per masked miss and must deny it quietly. Clients that may notice: `@moduleforge/users-gui` admin user-detail pages and any app GUI or server that treated 404 on these routes as "no such user".
- 2026-10-11, decode-wrapper-and-callers (3.2), planned items 3 and 4: `server.Decode` is now a wrapper over `apiresp.DecodeJSON` and all 16 body decodes use it. Every body route, including the public `/v1/auth/*` routes (login, register, anonymous, email-code request and verify, password-reset request and confirm), now rejects unknown JSON fields, trailing data after the first JSON value, and an empty body with 400 `invalid_input` and detail `invalid_json_body`. A body over 1 MiB gives 400 `invalid_input` with detail `body_too_large`; `POST` ssh-key register keeps its 32 KiB cap, now through `apiresp.WithMaxBytes` and with the same `body_too_large` detail (it was a bare 400). The literal "invalid JSON body" messages on `/v1/auth/*` become apiresp's fixed messages ("request body must be valid JSON" and siblings); the status and top-level code are unchanged. `POST /v1/user-accounts` no longer authorizes on decode failure: a malformed body is 400 for any authenticated caller (was 403 for a caller without create permission). `UserAccountService.AuthorizeCreate` stays (still used by `Create` and its tests). Client audit: the `@moduleforge/users-gui` request bodies and every app caller found (app-mfmanager scripts, onboard authclient and GUI, app-mfdemo, app-mfgit, app-mftodo) send only fields the server structs declare, with these exceptions. (a) `auth.resetPassword` in `@moduleforge/users-gui` sends `new_password` but the server reads `password`; before, the field was silently dropped and every GUI reset got 400 `users.password_too_short`; now it gets 400 `invalid_json_body` (unknown field). The server does not accept `new_password`; the GUI field is fixed by task 5.1. (b) `apps.addMember` sends `role` (server reads `roles`) and `apps.create`/`update` target routes this module does not serve; task 5.1 aligns them, and they have no callers today.
- 2026-10-11, user-accounts-and-self-shape (3.3), planned items 4, 5 and 6: (a) `POST /v1/user-accounts`: a malformed body, a missing or blank `email`, `given_name` or `family_name`, or a `password` under 12 characters now gives 400 `invalid_input` with the `users.*` detail codes (`users.email_required`, `users.given_name_required`, `users.family_name_required`, `users.password_too_short`), all reported together, to any authenticated caller before authorization. Old: 403 for a caller without create permission. A well-formed body from such a caller is still 403. (b) `PUT /v1/user-accounts/{uuid}`: a present-but-blank (after trim) `email`, `given_name` or `family_name` gives 400 with the same `users.*_required` codes (was stored). `UserAccountService.Update` also rejects blank fields for in-process callers, after its masked authorization. (c) Path UUIDs: a malformed `{uuid}` on `GET`/`PUT`/`DELETE /user-accounts/{uuid}`, `POST .../grant-admin`, `.../revoke-admin` and `.../assume` gives 400 with detail `invalid_uuid` on field `uuid` (was a bare 400), before any authorization. (d) `PUT /v1/self`: a present-but-blank `given_name` or `family_name` gives 400 with `natural_persons.given_name_required` or `natural_persons.family_name_required` before any lookup or authorization (was stored blank). A non-admin still updates their own names (the entity owns itself, so the owner arm grants `update`; pinned by an integration test). A corporation or service-account holder sending a name still gets 404 from mod-core after authorization (unchanged by this task). Assume session: the JWT subject is the admin and the assumed user is the sudo (effective) actor, but `PUT /v1/self` loads the account from the subject (the admin's own account), so a body carrying names is authorized as the assumed user against the admin's entity and gets 403 unless the assumed user holds `update` on it (mod-core's new `AuthorizeResolve`; before, the admin's own names were written). A body with no names is unaffected. Clients that may notice: app GUIs pairing mod-core `ProfileEditor` with this route (show the inline error), and anything that edits names while impersonating.
- 2026-10-11, apps-membership-shape (3.4), planned item 7: the four apps membership routes (`POST`/`GET /v1/apps/{uuid}/user-accounts`, `DELETE /v1/apps/{uuid}/user-accounts/{user_account_uuid}`, `PUT .../{user_account_uuid}/roles`) now parse the path UUIDs and decode and validate the body before the nil-target `Authorize`. A malformed `{uuid}` or `{user_account_uuid}` gives 400 `invalid_input` with detail `invalid_uuid` on the field (was a bare 400, and 403 for a non-admin caller). A malformed body, unknown field, or missing or non-UUID `user_uuid` on `POST` gives 400 to any authenticated caller (was 403 for a non-admin); the missing case keeps `users.user_uuid_required`, a bad format gives `invalid_uuid`. The app lookup is now only `coreQ.GetAppByUUID`, after authorization: an unknown app (or a uuid naming a non-app entity) is still 404 for an authorized admin and 403 for a caller without the grant. Archived apps are unchanged: neither the old `Resolve` plus `GetAppByUUID` pair nor the new lookup filters `archived_at`. `NewAppsHandler` no longer calls `entityResolver.AllowNotFound("app")` on the resolver shared with mod-core's services, so a plain `Resolve` of slug `app` on that resolver gives 403 on a miss (was 404 after this handler was built). `UpdateUserRoles` now decodes the body before the user-account lookup, so a malformed body wins over a 404 for an unknown user. Unchanged: a body `user_uuid` or path `user_account_uuid` that names no account still gives 404 after authorization (task 4.1 classifies it, D15). Clients that may notice: `@moduleforge/users-gui` and app GUIs that read the status of a non-admin's bad membership request.
- 2026-10-11, self-service-shape (3.5), planned items 8 and 9: (a) identities: `DELETE /v1/self/identities/{identity_uuid}` parses the UUID (400 `invalid_input`, detail `invalid_uuid` on field `identity_uuid`, was a bare 400) and `POST /v1/self/credential/password` decodes and validates the body before the step-up gate. A malformed body, or a missing or short `new_password`, now gives 400 with no step-up token (was 409 `users.step_up_required`) and does not consume a presented token. A missing `new_password` gains detail `users.new_password_required` (was a bare 400); a short one keeps `users.password_too_short`. (b) ssh keys: `POST /v1/self/ssh-keys`, `DELETE /v1/self/ssh-keys/{key_uuid}` and the self-targeting `POST`/`DELETE /v1/user-accounts/{uuid}/ssh-keys...` parse path UUIDs, decode the body and check `public_key` before the step-up gate; the same 400 without a token. A missing `public_key` gains detail `users.public_key_required` (was a bare 400). (c) `SSHKeyService.Register` runs `sshkey.Parse` and `sshkey.NormalizeLabel` before authorization: a malformed key or label gives 400 (`users.ssh_key_invalid`, `users.ssh_key_type_unsupported`, `users.ssh_key_label_*`) to a caller without `update` on the account (was 403), and to in-process callers; the duplicate-fingerprint 409 and the masked 403 for a well-formed request are unchanged. A malformed key from a self-route caller is still 409 step-up first when no token is presented (key parsing is service-side, after the handler's step-up gate). Unchanged: `current_password` 401, the provider-registry 404 in `StartLink` (configuration state, stays after step-up), and the 409 envelope. Clients that may notice: `@moduleforge/users-gui` credential and ssh-key forms that keyed off 409 for a bad body.
- 2026-10-11, oidc-config-credential-shape (3.6), planned item 10 (D7, D8): (a) `POST /v1/oidc-config/confirm`, `POST /v1/oidc-config/providers`, `PUT /v1/oidc-config/providers/{id}` now evaluate the body-independent credentials first (admin bearer via `AdminChecker`, then the `X-Setup-Token` header), then decode the body (400), then, only when neither authenticated, verify the body `setup_token` (401). An `AdminChecker` fault is 500 even when the body is malformed (it used to be 400 first). Documented exception to 401-before-400: a caller with no admin session and no header token whose body is malformed (or over-cap, trailing, or has an unknown key) gets 400, not 401, because the body is the only place its credential can be; tested. Credential-failure 401s are unchanged. A valid `X-Setup-Token` header now authenticates even if the body also carries a wrong `setup_token` (before, a non-empty body token shadowed the header); the token comparison and the one-shot clearing are unchanged. The GUI sends the token in both header and body, so it is unaffected. (b) Provider write bodies (`POST`/`PUT`) are capped at 1 MiB (400 `invalid_input`, detail `body_too_large`), reject trailing data after the first JSON value (detail `invalid_json_body`), and reject any top-level key outside `setup_token`, `id`, `display_name`, `issuer_url`, `client_id`, `client_secret`, `claim_style`, `scopes`, `enabled` (400, detail field = the offending key, code `invalid_json_body`, message "request body contains an unknown field"; one detail, the lexicographically first unknown key). Non-object JSON (an array, a string) is now 400 (was a decode error that also gave 400). A zero-byte body is still an empty object; a whitespace-only body is now 400 (was treated as empty). The GUI (`oidc-provider.ts`) sends only these keys. (c) `GET /v1/oidc-config/providers/{id}` with a malformed id is 400 `invalid_input` after the credential (was 404). (d) The 409 on `POST /v1/oidc-config/providers` for an existing id keeps status 409 and top-level code `conflict` and gains detail `{field: id, code: users.oidc_provider_exists, message: "provider id already exists; use PUT to update"}`; the top-level message becomes apiresp's fixed conflict text, and the GUI add-provider modal shows only the top-level message (followup filed). `check-server-error-literals.sh` now expects 3 carve-outs. (e) Recorded, not changed: `POST /oidc-config/confirm` still silently drops unknown provider ids in `enabled_providers` (200; no status chosen, followup filed). Unconstrained stateless inputs are unchanged and no constraints were added: provider-field wrong JSON types are still treated as absent by the merge helpers, and `scopes`, `claim_style`, `issuer_url`, `display_name` have no format limits (the unconstrained `purpose`, email format, `device_id` and `roles` inputs of the auth and apps routes are recorded in the audit as F9). Clients that may notice: `@moduleforge/users-gui` OIDC config page, external setup scripts that call these routes with extra keys or an oversized body.
- 2026-10-11, public-auth-error-literals (3.7), planned item 11 (D12, F3): the literal `server.Error`/`server.ErrorWithDetails` calls in `api/internal/handlers/auth` now go through `apiresp`, except the documented keeps below. Status and top-level `code` are unchanged everywhere; messages and details change as follows. (a) Every 500 `internal_error` (36 sites in `register`, `login`, `emailcode`, `reset`, `anonymous` and `oidc`, including the OIDC link-mode and the frontend-redirect URL-parse faults) now carries apiresp's fixed message "an internal error occurred" instead of the per-site text ("failed to look up user account", "token issuance failed", and so on); the specific cause is logged server-side. (b) `POST /v1/auth/login` with a missing email or password gives 400 `invalid_input` with one detail per missing field: `users.email_required` (field `email`) and new `users.password_required` (field `password`) (was no details, message "email and password are required"). (c) `POST /v1/auth/email-code/verify` with a missing email or code gives 400 with new details `users.email_required` and new `users.code_required` (field `code`) (was no details). (d) `POST /v1/auth/password-reset/confirm` with a missing token gives 400 with new detail `users.token_required` (field `token`) (was no details); the short-password 400 keeps detail `users.password_too_short`. (e) `POST /v1/auth/anonymous` with a missing `device_id` keeps detail `users.device_id_required`. (f) `GET /v1/auth/oidc/{provider}/start`: an unknown or unavailable provider is 404 `not_found` with apiresp's fixed message (was "unknown provider"); the 400 no longer echoes the internal error text and now carries one detail, field `return`, code new `users.oidc_start_invalid`, message "the start request is invalid" (was the raw `AuthorizeURL` error text such as "oauth: return path must begin with '/'..."). (g) `GET /v1/auth/oidc/{provider}/callback` JSON error paths: unknown provider 404 `not_found` (fixed message); missing `code` or `state` 400 with new detail field `code`, code `users.oidc_code_or_state_required`; missing state cookie 400 with new detail field `state_cookie`, code `users.oidc_state_cookie_required`; invalid or expired state 400 with new detail field `state`, code `users.oidc_state_invalid`. Every converted 400 has the fixed top-level message "one or more fields are invalid". Redirects, cookies and the test-mode `error` redirect parameter are unchanged. Kept as literals (11, each marked `literal-keep:` in source and counted by `check-server-error-literals.sh`, which now also scans `handlers/auth` with an expected count of 11 beside the unchanged 3 `identities.go` carve-outs): the 6 credential-failure 401s (`login` invalid email or password x2, `emailcode` invalid or expired code x3, `reset` invalid or expired reset token x1), asserted or displayed by the GUI; and, by the manager's decision on flag F3, the 5 `register` literals (400 `users.email_required`, `users.password_too_short`, `users.given_name_required`, `users.family_name_required`, and the 409 `users.email_taken`), because `register-form.tsx` shows the server message verbatim and converting would change user-visible text. Action-required envelopes are not touched. Clients that may notice: any client that matched the old 500 or OIDC 4xx message text, and `docs/cookie-path.md` readers (updated).
