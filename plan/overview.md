# Forgot-Password, Reset-Password, and Email-Code UI Components — Plan Overview

## Purpose and scope

`gui/src` currently exports `LoginForm`, `RegisterForm`, `AuthPage`, and `OidcCallbackPage` (added by the `login-register-ui` plan) but ships no ready-to-use UI for the password-recovery and email-one-time-code flows. `app-mfdemo` (a separate, sibling git repository outside this project's `project_root`) has already hand-built these pages against the raw API client: `app-mfdemo/src/app/auth/forgot-password/page.tsx`, `.../reset/page.tsx`, and `.../email-code/page.tsx`. Per `docs/architecture.md`'s GUI component library section, this is explicitly the gap the `login-register-ui` plan left open ("Password reset, profile management, and email one-time-code login are not yet part of this surface").

This plan adds three new components to `gui/src/components/`, exported from `gui/src/index.ts`, generalizing those three `app-mfdemo` reference pages into reusable library components: `ForgotPasswordPage`, `ResetPasswordPage`, and `EmailCodePage`. The `app-mfdemo` pages (transcribed in full in the originating change request, since this project has no filesystem access to that sibling repository) serve as the source of truth for expected UX, form fields, validation behavior, and state transitions.

The underlying API client methods (`api.auth.forgotPassword`, `api.auth.resetPassword`, `api.auth.requestEmailCode`, `api.auth.verifyEmailCode`) and their request/response types already exist in `gui/src/lib/api.ts` and are already exported from `gui/src/index.ts`. This is a UI-layer-only plan — no API client changes are in scope.

Explicitly out of scope:
- Any changes to `app-mfdemo` itself — a separate sibling git repository outside this project's `project_root`. That migration (updating `app-mfdemo/src/app/auth/forgot-password/page.tsx`, `.../reset/page.tsx`, and `.../email-code/page.tsx` to consume these new exports) is being planned separately, as a directly-requested second plan sequenced to start only after this plan's component API is finalized. Per explicit instruction, no `plan/followups.yaml` item is added for it this time (unlike the `login-register-ui` precedent, which recorded such a followup for a different set of pages, tagged `login-register-ui-consumer-migration`).
- Any change to the API client (`gui/src/lib/api.ts`) or the API server itself — both already fully support these flows.

## Key decisions

1. **Page-level, self-contained components (not bare forms).** `ForgotPasswordPage`, `ResetPasswordPage`, and `EmailCodePage` each own their own `Card` (from `@moduleforge/core-gui`) and, where applicable, their own internal step/state transitions — mirroring `AuthPage`/`OidcCallbackPage`'s pattern (full-page composition, router-agnostic callback props) rather than `LoginForm`/`RegisterForm`'s bare-form pattern (no `Card`, single view, meant to be composed inside a consumer- or `AuthPage`-provided `Card`). This is confirmed, not overridden, after reading all four existing components: `ForgotPasswordPage` has two distinct `Card` bodies (request / submitted-confirmation), and `EmailCodePage` has two distinct `Card` bodies (request / verify) — both are exactly the shape `AuthPage` already established for multi-view, single-component pages. `ResetPasswordPage` has only one view, but is still page-level (owns its own `Card`) for API consistency with its two siblings and because, like `OidcCallbackPage`, it is a standalone routing target (the emailed reset-link's landing page) rather than a fragment meant to be embedded inside another component's `Card`.
2. **Naming matches the page-level pattern**: `ForgotPasswordPage`, `ResetPasswordPage`, `EmailCodePage` (not `*Form`), consistent with `AuthPage`/`OidcCallbackPage`.
3. **Router-agnostic callback pattern, uniformly applied.** No component imports `next/navigation` or `next/link`. Every navigation-adjacent affordance is a callback prop, all following the codebase-wide convention (`RequireAuth.onUnauthenticated`, `ClientLayout.onNavigateToConfig`, `AuthProvider.onNavigate`, `LoginForm`/`RegisterForm`/`AuthPage`'s `onSuccess`/`onAuthenticated`) of being **optional, defaulting to a no-op** — the sole existing exception, `OidcCallbackPage`'s required `onComplete`/`onError`, is a special case (that page has no other reason to exist once the callback fires) and does not apply here, since all three new components have substantial standing UI. Concretely:
   - A new `onNavigateToLogin?: () => void` prop (optional, no-op default) is added to all three components for their "Back to sign in" / "Sign in with password instead" footer links, rendered as `<button type="button">` elements (matching `AuthPage`'s existing mode-toggle footer button styling exactly) rather than real anchors — introducing a `LinkComponent`-style prop (as `SidebarNav` uses) was considered and rejected as unnecessary API surface for a single, low-frequency footer prompt, and because the request's explicit constraint is to mirror the `onSuccess`/`onError`/`onComplete` callback-prop pattern, not the `LinkComponent` pattern.
   - `ResetPasswordPage` and `EmailCodePage` additionally get an `onSuccess?: () => void` prop (optional, no-op default) fired after the underlying action succeeds (password reset confirmed; code verified and session established), replacing the reference pages' `router.push(...)` calls — mirrors `LoginForm`/`RegisterForm`'s `onSuccess` exactly.
   - `ForgotPasswordPage` has no `onSuccess`-equivalent: its "submitted" confirmation view is rendered in place (internal state), exactly like `AuthPage`'s internal mode toggle — there is no "success" moment that hands control to the consumer beyond the optional "Back to sign in" click.
4. **`ResetPasswordPage`'s `token` is a required prop**, not read via `useSearchParams` internally — the consuming app's own page (in `app-mfdemo`, out of scope here) reads it from the URL and passes it in. The component still performs the reference page's defensive `if (!token)` empty-string check before submitting, since a required *TypeScript* prop does not prevent a caller from passing an empty string at runtime (e.g. a missing query parameter).
5. **Password minimum length is 12 characters**, confirmed directly against the current server-side rule at `api/internal/service/user_accounts.go` line 157 (`if in.Password != nil && len(*in.Password) < 12`) rather than trusting the request's transcription — unchanged since the `login-register-ui` plan's `RegisterForm` was built against the same rule. `ResetPasswordPage` mirrors this exactly, matching `RegisterForm`'s existing client-side-mirrors-server comment convention.
6. **A Ladle story per new component**, following the exact convention of `LoginForm.stories.tsx`/`RegisterForm.stories.tsx`/`AuthPage.stories.tsx`: a PascalCase `<ComponentName>.stories.tsx` file under `gui/src/stories/`, each story wrapping the component in `<AuthProvider>` (only `EmailCodePage` needs it, for `useAuth()`; `ForgotPasswordPage`/`ResetPasswordPage` do not call `useAuth()` and so do not need the provider), with a comment noting that submission will fail with a `network_error` in the story environment (no live API) — exactly as the existing stories note. `OidcCallbackPage` has no story (it depends on `window.location` fragment/query state that can't be meaningfully faked at mount in Ladle); none of these three new components have that constraint, so all three get stories.
7. **A second, `doc-updates` phase is required.** `docs/architecture.md`'s GUI component library paragraph currently states "Password reset, profile management, and email one-time-code login are not yet part of this surface" — this becomes stale the moment these three components ship. This also independently satisfies this skill's own Phase 4 architectural-implications check (the plan modifies a public component-library API boundary), so a `doc-updates` phase is added, following the `login-register-ui` plan's precedent exactly (same phase slug, same task shape, `sonnet-high` tier).
