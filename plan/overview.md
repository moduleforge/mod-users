# Self-Route Manifest Wiring — Plan Overview

## Purpose and scope

Wire the mod-users `GET/PUT /v1/self` endpoints into the manifest-driven mfgen
codegen path so that any app composing mod-users (starting with app-mftodo)
actually receives `/self` routes in its generated server. Today the business
logic exists (`api/internal/handlers/self.go`'s `SelfHandler.Get`/`Put`) and a
hand-written non-generated dev server (`api/cmd/server/main.go`) demonstrates the
intended wiring, but `moduleforge.module.yaml` has **no** `register:` entry for
`/self`, so mfgen never emits `/self` into any generated `main.go` (confirmed:
zero `self` hits in `app-mftodo/cmd/server/main.go`).

### Clarified requirements

**Must change**
- Add a `handlers.RegisterSelfRoutes` function (new, in
  `api/internal/handlers/`) that mounts `GET /self` and `PUT /self`, accepting the
  verified-email middleware as a parameter so it can apply that gate to `PUT` only.
- Add manifest wiring to `moduleforge.module.yaml`: a `selfHandler` service entry
  (constructing `*handlers.SelfHandler`), a `/v1` route `register:` entry for
  `RegisterSelfRoutes`, and a `coreServices` `requires.services` entry.
- Update docs: `docs/architecture.md`, `docs/mod-users-spec.md`, and `AGENTS.md`
  to record (a) the `GET`-unverified / `PUT`-verified `/self` contract and (b) the
  `expr:` register-arg pattern as the sanctioned way to express a per-route
  middleware split within a single prefix.
- Reconcile the `TODO(generated)` markers in the hand-written dev server
  (`api/cmd/server/main.go`) now that real manifest registration exists.

**Must NOT change**
- Nothing outside the `mod-users/` tree: no edits to `mfgen/`, `app-mftodo/`, or
  any sibling module/app. The mfgen **schema and generator are used as-is** — the
  plan is scoped to `mod-users` only. (If the goal turned out to need an mfgen
  change, this plan would halt with `needs input`; verification shows it does
  not — see [mfgen expr pattern notes](./notes/mfgen-expr-middleware-pattern.md).)
- app-mftodo's generated `main.go` is regenerated by a separate process/agent;
  this plan does not touch it. Any mfgen run against app-mftodo is
  verification-only, never a deliverable.

**Success criteria**
- `moduleforge.module.yaml` declares a `register: handlers.RegisterSelfRoutes`
  entry whose `register_args` pass `requireVerifiedEmail` via the `expr:` arg-kind,
  with group-level `middleware:` = `requireOIDCConfirmed` + `requireAuth` only.
- `handlers.RegisterSelfRoutes` compiles (`make build.api`) and applies
  `requireVerifiedEmail` to `PUT /self` only, leaving `GET /self` reachable to
  unverified accounts.
- The expected generated snippet (documented in the notes) would produce
  `GET /v1/self` gated by `requireOIDCConfirmed`+`requireAuth`, and `PUT /v1/self`
  additionally gated by `requireVerifiedEmail`.
- Docs record the `/self` contract and the `expr:` per-route-middleware pattern.

**Hard constraints (from the request)**
- `GET /self` must remain reachable to accounts with an unverified email; `PUT
  /self` must require a verified email. This split is preserved exactly.
- No mfgen schema/generator change. Verified unnecessary — see the notes.

### Key verification result

Source-level verification against the real mfgen code and the already-generated
`app-mftodo/cmd/server/main.go` confirms the manifest-only approach works with the
current generator. Details, exact syntax, expected output, and one documented
fragility are in
[mfgen expr middleware-split pattern notes](./notes/mfgen-expr-middleware-pattern.md).

## Overview

Two phases, run in sequence (docs depend on the final manifest wiring).

### Phase 1 — Self-Route Wiring

Single task (`001-wire-self-routes-manifest`): the whole code/manifest change,
kept as one coherent unit because the manifest `register:` entry and the Go
function it names are interdependent.
- Create `api/internal/handlers/self_routes.go` with `RegisterSelfRoutes(r,
  h *SelfHandler, requireVerifiedEmail func(http.Handler) http.Handler)`.
- Add to `moduleforge.module.yaml`: `selfHandler` service, `/v1` route
  `register:` entry (`register_args: [expr:requireVerifiedEmail]`, `middleware:
  [requireOIDCConfirmed, requireAuth]`), and `coreServices` under
  `requires.services`.
- Reconcile the dev-server `TODO(generated)` markers: **decision** — leave the
  working hand-written `GET/PUT /self` block in place (mfgen does not regenerate
  this standalone dev server, so removing it would break it) and add a reference
  comment noting the manifest now expresses this wiring via `RegisterSelfRoutes`,
  consistent with the sibling auth/oidc-config/account `TODO(generated)` markers.
- Marked `architectural_impact: true` (touches the auth-gating topology and the
  API route surface documented in `docs/architecture.md`).

### Phase 2 — Documentation Updates

Single task (`001-update-architecture-docs`, added by the architectural
implications check): update `docs/architecture.md`, `docs/mod-users-spec.md`, and
`AGENTS.md` to document the `/self` `GET`-unverified/`PUT`-verified contract and
the sanctioned `expr:` per-route middleware-split manifest pattern. Depends on
Phase 1 landing so the docs describe the final manifest entry accurately.

No parallel-eligible tasks (each phase has one task; Phase 2 depends on Phase 1).
