# mod-users architecture

## Overview

`mod-users` is a ModuleForge module that provides user identity, account management, and authentication as a composable unit. A host application integrates it by mounting the Go model migrations, wiring the Go API services, and importing the React component library. The module ships three sub-projects — `model`, `api`, and `gui` — each independently consumable and built to the ModuleForge module contract described in [mod-core architecture](./mf-standards/architecture.md). A demo application (`app-mfdemo`) that wires the module end-to-end lives in a separate project at the aggregate level.

Identity follows mod-core's [identity model](https://github.com/moduleforge/mod-core/blob/main/docs/architecture/identity-model.md): **principals** (users, service accounts, system actors) authenticate with **credentials**, hold **sessions**, and act only through **profiles** (a personal profile, plus one per party they belong to). A session is the unit of revocation, carried to the API as a short-lived EdDSA access token that is re-checked against the database on every request; [Sessions and tokens](./architecture/sessions-and-tokens.md) records how sessions, tokens, liveness, step-up, impersonation and the first-run bootstrap work. The sections below cover the schema, the routes, the authorization engine's consumer side and the recorded design decisions.

### Runtime service dependencies

Beyond the cross-module *schema* composition described under [Data model](#data-model) below, `mod-users` also declares runtime *service*-level dependencies in `moduleforge.module.yaml`'s `requires.services` — Go service instances that a composing host application must supply (typically from `mod-core` and `authz-module`) before `mod-users`' own `provides.services` can be constructed. As of this writing, `requires.services` lists:

| Service | Source module | Used by | Purpose |
|---|---|---|---|
| `naturalPersonService` | mod-core | `userService` | `coreservice.NaturalPersonServicer` — creates the user's own `natural_person` record at registration, guest upgrade and just-in-time OIDC creation |
| `displayRegistry` | mod-core | `userService` | `*display.Registry` — mod-users registers display renderers for the `user` and `profile` entity types on it (a user renders as the person's name, else the primary email, else "Guest"; a profile as "holder (Personal)" or "holder @ party") |
| `coreServices` | mod-core | `bootstrapOrganizationService` | `*coreservice.Services` — the composite core-services aggregate; the setup-token bootstrap creates the operator organization through its trusted `Organization.CreateInTx` |

`requires.infra` (`pool`, `opReg`, `smtp`, `cfg`) covers infrastructure singletons rather than services and is not enumerated here; see `moduleforge.module.yaml` directly for the current list. This table reflects the manifest at the time of writing — treat `moduleforge.module.yaml`'s `requires:` block as the source of truth if the two ever disagree.

### Configuration and secrets bootstrap

`config.Load()`'s Postgres connection string resolves `MFAPP_DATABASE_URL` when set, else `DB_URL` — both names are supported permanently, not as a deprecation window: `MFAPP_DATABASE_URL` is the name the `app-mfmanager` catalog-deploy engine injects into the apps it manages, while `DB_URL` remains the permanent name for a self-hosted or non-catalog Postgres connection, including `app-mfmanager`'s own bootstrap connection. When `JWT_SIGNING_KEY` is not supplied via the environment and a resolved DB URL is present, `Load()` fetches-or-generates-and-durably-persists the Ed25519 access-token signing key from Postgres (the single-row `mod_users.auth_signing_keys` table; see [Data model](#data-model)), using its own short-lived, dedicated connection rather than the pool — the pool does not exist yet at this point in every generated composition root, since `Load()` is the first call in every generated `main.go`, ahead of both the pool and this module's own migrations. This is a **pre-pool, per-boot Postgres dependency inside `Load()`**, not merely a table: `Load()` is otherwise pure and network-free, and this bootstrap path is the first place in a generated `main.go` that can talk to the database at all. An explicit `JWT_SIGNING_KEY` always wins and makes `Load()` skip the database; a persisted key that fails to parse fails loudly rather than being silently regenerated (regenerating would invalidate every outstanding access token), a `JWT_SIGNING_KEY` that is set but invalid is reported and never silently replaced by the persisted key, and an unreachable database on this path fails `Load()` itself — a DB-dependent failure mode a composing app's boot may not have had before. Concurrent first boots converge on one key: the bootstrap holds a session-level advisory lock, creates the schema and table idempotently (the `auth_signing_keys` section of the `0100_baseline.sql` migration uses `CREATE TABLE IF NOT EXISTS`, deliberately, because `Load()` runs before this module's own migrations apply), inserts with `ON CONFLICT DO NOTHING`, and every caller reads the winning row back.

**Access-token algorithm.** Access tokens are EdDSA (Ed25519) JWTs only; HS256 and the `JWT_ALG` switch are removed. A token is a carrier for a server-side session or credential, never authoritative on its own (see [the access token](./architecture/sessions-and-tokens.md#the-access-token)). `JWT_SIGNING_KID` stamps the `kid` header, and `JWT_VERIFY_PUBLIC_KEYS` adds public keys accepted for verification (rotation, verify-only services). The verifier pins `EdDSA`, so a public-key-only verifier never accepts HS256 or `alg: none`. `JWT_SECRET` is optional and keys only the OAuth `state` parameter of the OIDC flow; when unset, that key is derived from the signing key (D19). The session and token lifetimes are `AUTH_*` settings (`AUTH_ACCESS_TOKEN_TTL`, at most one hour; `AUTH_SESSION_MAX_AGE`; `AUTH_SESSION_IDLE_TIMEOUT`; `AUTH_CLIENT_CREDENTIALS_TTL`; `AUTH_IMPERSONATION_TTL` and `AUTH_IMPERSONATION_MAX`; `AUTH_SELF_SERVICE_MAX_AUTH_AGE`), listed with their defaults in the [README](../README.md#configuration). Operator and integrator details: [jwt-eddsa.md](./jwt-eddsa.md).

## Sub-project layout

| Sub-project | Language | What it owns | What it exposes |
|---|---|---|---|
| `model/` | Go | Postgres schema, goose migrations, sqlc query code | Go package with typed query functions and model types |
| `api/` | Go | HTTP handlers, business-logic services, auth middleware | Mountable HTTP routes; Go service constructors |
| `gui/` | TypeScript / React | UI components for auth flows and user management | `@moduleforge/users-gui` npm package |
The sub-projects have a layered dependency: `api` imports `model`; `gui` is independent of the Go code. The demo application (`app-mfdemo`, a separate project at the aggregate level) depends on both the running `api` and the `gui` library.

## Data model

The Postgres schema lives in `model/migrations/` (managed with goose). The sqlc-generated Go query code is in `model/db/`. Every table, function and trigger this module owns is created in the `mod_users` schema and referenced schema-qualified; the mod-core and mod-authz tables it reads (`principals`, `profiles`, `system_actors`, `platform_settings`, `profile_policy_confirmations`, `apps`, `legal_entities`, `natural_persons`, `grants`, `authz_operations`) are referenced as `public.*`.

| Table (in `mod_users`) | Purpose |
|---|---|
| `users` | The `user` principal subtype (the `user` entity type and the `principals` row are mod-core's). Holds `person_id` (the user's own `natural_person` record; not unique, null for a guest or a managed user), `managing_party_id` (the party that owns and manages a managed user; immutable), `is_guest` (may only go from true to false), `default_profile_id` and `default_app_id` |
| `user_identifiers` | Email, phone and username identifiers of a user (`kind`, `value_canon`, `verified_at`, `is_primary`). `UNIQUE (kind, value_canon)` keeps one account per canonical address; at most one primary email per user. Only users have identifiers. The table name and the columns `user_id`, `kind`, `value_canon`, `verified_at` and `is_primary` are a read surface other modules (billing, tokens) query directly; all writes go through this module's services |
| `credential_kinds` | Seeded registry of credential kinds (`password`, `email_otp`, `oidc`, `ssh_key`, `api_key`, `anon`) with each kind's class (interactive or non-interactive), factor class, base assurance level (`base_acr`), `amr` value and whether a service account may hold it |
| `credentials` and `cred_password`, `cred_email_otp`, `cred_oidc`, `cred_ssh_key`, `cred_api_key`, `cred_anon` | One row per credential (`principal_id`, `kind`, `label`, `confined_to_party_id`, `default_profile_id`, `last_used_at`, `expires_at`, `revoked_at`, `revoke_reason`) plus one per-kind subtable row. Credentials are revoked, never deleted. Partial unique indexes over the `active` flag (kept in step with `revoked_at` by trigger) make an OIDC `(issuer, subject)` pair and an SSH key fingerprint unique among active credentials, and bound one active password per identifier |
| `auth_challenges` | Short-lived one-time challenges: emailed codes (`email_code`, `verify_identifier`, `step_up`), password-reset tokens and OIDC `login_handoff` codes. Each carries `failed_attempts`; request cooldown is enforced atomically in the database by `create_challenge_with_cooldown` |
| `oidc_config`, `oidc_providers` | Per-deployment OIDC configuration (opt-out flag, the setup-token hash) and per-provider overrides. A provider can be bound to a party (`party_id`), has a just-in-time creation mode (`jit_mode`: `none`, `byo` or `managed`; `managed` needs a party) and a `trust_acr` flag |
| `party_authn_policies` | A party's authentication policy: `credential_rule` (`any`, `authorized` or `provider`, the last with `required_oidc_provider_id`) and `min_acr`. No row means `any` and `min_acr` 1 |
| `credential_party_authorizations` | Which credentials a party administrator (or the credential's holder, by the two-door rule) has authorized for the party's `authorized` rule |
| `sessions`, `session_factors`, `session_refresh_tokens` | The session (the revocation unit, with `acr`, `amr`, `auth_time`, expiry, revoke reason and the impersonation columns), the credentials that authenticated it, and the per-tab refresh tokens. See [Sessions and tokens](./architecture/sessions-and-tokens.md) |
| `auth_signing_keys` | Private, single-row table holding the persisted Ed25519 access-token signing key used when `JWT_SIGNING_KEY` is not supplied via the environment — the persistence target of `Load()`'s fetch-or-generate-persist bootstrap (see [Configuration and secrets bootstrap](#configuration-and-secrets-bootstrap)). Operational, not domain data |

What the former model kept in `user_accounts`, `auth_local`, `email_codes`, `password_resets`, `auth_oidc_identities`, `anon_tokens`, `apps_user_accounts`, `mod_users.ssh_public_keys`, a mod-users copy of `system_actors` and `auth_jwt_secrets` is gone: there is no migration of data, the baseline was rewritten in place. A user's name lives on their `natural_person` record, not on the user; app access is a `login` grant on the app entity (see [the app `login` gate](#authentication-flow)) rather than a membership join table.

**Database invariants.** The rules that must hold whichever writer touches the tables are enforced by triggers and constraints, with module-specific SQLSTATE codes (mirroring the module's migration range 100 to 199) that `usersservice` exposes as `IsSessionInvariantError`, `IsCredentialInvariantError` and `IsUserInvariantError`:

- `MF101` (session invariant): an impersonation session's parent is never itself an impersonation (no nesting), the impersonated profile is held by the session's principal, the principal and the impersonation columns are immutable, only a `user` has a session, and a session factor's credential belongs to the session's principal.
- `MF102` (credential invariant): a credential's `principal_id` and `kind` are immutable; a service account holds only kinds marked `service_allowed`; a system actor holds none; a guest holds only `anon`; a non-guest user can never gain a new `anon`; `default_profile_id` names a profile the principal holds; the per-kind subtable row matches the credential's kind.
- `MF103` (user invariant): the entity descends from `user`; the user is owned by itself (bring-your-own) or by its `managing_party_id` (managed); `default_profile_id` names a profile the user holds; a guest has no person or managing party; a managed user has no personal profile and party profiles only in its managing party, a guest has no party profile, and a bring-your-own user has exactly one personal profile (checked at commit).

Unique violations stay `23505` and map to `409` by named index: `user_identifiers_kind_value_uq` (`users.identifier_taken`), `cred_oidc_active_issuer_subject_uq` (`users.oidc_identity_in_use`), `cred_ssh_key_active_fingerprint_uq` (`users.ssh_key_in_use`), and mod-core's `profiles_one_open_per_holder_party` (`users.profile_exists`).

**SQL functions.** The shared rules live once in SQL so single-row and list paths cannot drift: `profile_availability` and `credential_profile_availability` (the lock reasons of [Profile availability](./architecture/sessions-and-tokens.md#profile-availability)), `session_liveness` and `credential_liveness` (the one-round-trip per-request check), `session_acr`, `session_policy_factors`, and the owning-party gate used by the authorization engine (`session_meets_party_policy`, `owning_party_gate`, `access_row_permitted`; see [API layer](#api-layer)). The module also stubs `public.accessible_user_ids_for_actor`, the list-access function of the `user` type, which the host's `setup.ApplyFuncs` replaces at startup.

**Everything is `mod_users`.** There is one placement rule for this module's tables: module-owned tables belong in `mod_users` and are schema-qualified, per the ecosystem's `docs-mf-standards/architecture/schema-ownership-design.md` standard. The earlier mixed layout (older tables unqualified in `public`, SSH keys alone in `mod_users`) is gone, which also removes the per-function `current_schema()` search-path baking: trigger and SQL functions are `SECURITY INVOKER` with `search_path = pg_catalog, pg_temp` and fully qualified names. See [D1: schema placement](./architecture/ssh-keys.md#d1-schema-placement) for the rationale, including the operational consequence for a composing application's runtime database role and its backup/reset/test tooling.

**Baseline rewrite.** While the module was still pre-release, the migration history was collapsed into the single baseline `model/migrations/sql/0100_baseline.sql`, and the identity-model rewrite replaced it in place (there are no incremental migrations on top of it). A database that recorded earlier versions in `goose_db_version_users` must be dropped and recreated (`make clean.data` for the local stack); applying the baseline over it fails with "already exists".

**Operational requirements for composing hosts.** The baseline migration issues no `GRANT`; a composing host's own provisioning owns privileges on `mod_users`.

- **Hosts running the API** need `USAGE` on schema `mod_users` and table privileges on its tables and on the sequences behind its `BIGSERIAL` ids. Credentials are revoked with an `UPDATE`, never deleted, so the credential tables do not need `DELETE`.
- **Resolve-only hosts** (consume `sshKeyResolver`, per [D11](./architecture/ssh-keys.md#d11-resolver-consumer-contract)) need `USAGE` on `mod_users` and `SELECT` on the tables the resolver reads: `credentials` and `cred_ssh_key` for the lookup, and, because `credential_profile_availability` is `SECURITY INVOKER`, the tables it reads (`credential_kinds`, `cred_oidc`, `party_authn_policies`, `credential_party_authorizations`), plus read access to the mod-core `public` tables `entities`, `principals`, `profiles` and `profile_policy_confirmations`.
- **Failure mode.** Without these privileges, resolution fails with a database permission error, not the `ErrUnknownSSHKey` "unknown key" sentinel. A host that lacks the write privileges should keep the write routes unreachable rather than let them return a `500`.
- **Tooling scoped to `public` misses the tables.** Backup, restore, reset, truncate, and test-fixture tooling that enumerates this module's tables by scanning `public` will not see them. Composing hosts should check: `pg_dump` schema filters (`-n`) include `mod_users`; reset and truncate lists name `mod_users` tables; no code relies on `search_path` to resolve them (this module always schema-qualifies); test-database teardown drops or truncates `mod_users` too.
- **mod-users' own tooling.** As of this writing the repository's scripts, Makefiles, `deploy/` manifests, and Go test helpers do not enumerate, dump, truncate, reset, or grant on tables by schema, so none assumes `public` only.

Internal IDs are integers (joins only, never sent in responses). External IDs are UUIDs. Cross-module schema dependencies (the `principals` and `profiles` tables, `legal_entities` and `natural_persons`, `apps`) are resolved by the host application's migration composition step, not by tight coupling: this module's manifest declares `after: [core]` (see `moduleforge.module.yaml`) so mod-core's migrations run before this module's, satisfying `users.person_id`, `users.managing_party_id`, `users.default_app_id` and the credential and party columns that reference them at composition time. `apps` is defined and CRUD-managed by mod-core; this module keeps no local `apps` table or query.

The system actors are mod-core's: the `system_actor` entity type, the `system_actors` table and the seeded `anonymous` actor (slug `anonymous`, with its personal profile) belong to mod-core, which also guarantees by trigger that an entity is never owned by a system actor (mod-core's owner-domain rule subsumes the `entities_no_system_actor_owner` guard this module used to carry). mod-users holds no copy: its `anonymousActor` service resolves the seeded actor by slug at boot, through `coredb.GetSystemActorBySlug`, and hard-fails startup if the actor cannot be found or holds any grant. The zero-grants property is verified only *once*, at process boot, rather than by a database constraint, because mod-authz's `grants` table is created by a migration that runs after mod-users' own 100–199 migration range. A system actor never authenticates and holds no credential (`MF102`), and it is deliberately excluded from the list-access generation slugs in `api/cmd/server/main.go`, so no `accessible_system_actor_ids_for_actor` function is generated for it and it stays invisible to every list path.

## API layer

The HTTP API is defined in `api/openapi.yaml`. Handlers live in `api/internal/handlers/`; business logic in `api/internal/service/`. Every route requires an `Authorization: Bearer <jwt>` header except the health probes, the `/v1/auth/*` sign-in, registration and token routes, `/v1/bootstrap*` and `/v1/oidc-config*`; no route reads an authentication cookie, and this module does not mount any of its own routes behind the tokenless mechanism described below. mod-users additionally *exports* an opt-in `resolveOrAnonymous` middleware (facade: `auth.NewResolveOrAnonymous`) that other ModuleForge modules can compose onto their own `scope: public` route groups to accept a genuinely tokenless request — no `Authorization` header at all — and still resolve a real, zero-authority actor identity before their authorization checks run. See [Authentication flow](#authentication-flow) for the full behavior.

Removed routes answer `404`: `/v1/self*`, `/v1/user-accounts*` (the account administration and grant-admin routes and the operator SSH-key routes included), `/v1/assume`, `/v1/apps/{uuid}/user-accounts*` and `/v1/anonymous-demo`. Platform administrators are now operator-party profiles plus grants; app membership is a `login` grant through mod-authz's grants API.

mod-users also *exports* `sshKeyResolver` (facade: `usersservice.SSHKeyResolver` / `usersservice.NewSSHKeyResolver`), a second cross-module integration point alongside `resolveOrAnonymous` above. Unlike that middleware, `sshKeyResolver` is not consumed via HTTP — a composing application's own transport code (for example `app-mfgit`/`mod-repos`' SSH server) calls its `ResolveCredential` method directly, once per candidate SSH key a client offers during a handshake, to resolve that key to the active `ssh_key` credential that registered it, and then `AuthContextForOwner` to derive the `AuthContext` (the acting profile follows the repository's owner, honoring party policy and credential confinement) a repository operation runs as. No `mod-users` route consumes this service itself. `ResolveCredential` is pre-authentication, side-effect-free, and uncached by design — see [D11: resolver consumer contract](./architecture/ssh-keys.md#d11-resolver-consumer-contract) for the full contract and the composing transport's own rate-limiting and candidate-key-capping precondition.

mod-users also *exports* the `localAuthz` facade (`localAuthz.Authorizer` / `localAuthz.New`), the grants-table implementation of mod-core's `coreAuthz.Authorizer`, and, alongside it, the `localAuthz.TypeAuthorizer` capability interface, whose single method `AuthorizeType(ctx, operation, typeID)` answers type-level `create`/`list` checks distinctly from the entity-level `Authorize`, from wildcard grants and from grants on the exact type's entity. A consumer that holds only a `coreAuthz.Authorizer` asserts `TypeAuthorizer` and otherwise falls back to a nil target, which is wildcard-only and so denies type-grant holders, as described in [D12](#key-decisions). A target is admitted through a wildcard grant, an entity grant (a grant on a type's entity also confers the operation over every instance of exactly that type, see [D13](#key-decisions)), an owned-scope grant on the target's owner (restricted to a target type and, with `include_subtypes`, its descendants; it never reaches the owner's own record), or the own arm. The engine's only subject is the acting profile (`opctx.AuthContext.ProfileID`; under impersonation, the impersonated profile), never the principal. The `Authorizer` also implements mod-core's `coreAuthz.OwnerScopedTypeAuthorizer` (`AuthorizeTypeIn(ctx, operation, typeID, ownerID)`: create and list of a type within an owner, through the wildcard arm, a type-entity grant, an owned-scope grant on the owner with a matching type, or the own arm), so mod-core's `authz.AuthorizeTypeIn` helper no longer falls back to `AuthorizeType` for it. Every check first runs a prelude: the operation-level assurance gate (`min_acr`, `max_auth_age`; refused with `409 users.step_up_required`) for every context except a trusted system actor and the anonymous context, then, when the check names an owner, the owning-party gate (`mod_users.session_meets_party_policy`): an acting profile outside the target's owning party must meet that party's `credential_rule` and `min_acr` with its session's factors or its credential, or the check is refused with `403`. A party is its own owning party: when the target is itself a `legal_entity`, it is gated by its own policy as well as by its direct owner's, so an outside collaborator holding `update` on a restrictive party's record cannot change that party (for example its authn policy) from a session that does not meet it. Nested ownership is one level only: the gate checks the target (when it is a party) and its direct owner, never the owner's owner. Platform operator profiles (`core_is_operator_profile`) are exempt from this gate: a customer party's policy never binds the operator, so the platform can always administer, support and impersonate; operation-level `min_acr` and step-up still apply, and non-operator outside collaborators stay gated. An impersonation session holds no factors of its own: the impersonated profile's rules apply to every operation, and both this gate and the profile's own party gate (`profile_availability`) are evaluated on the administrator's parent session (`impersonator_session_id`): its unrevoked factors for the `credential_rule`, its acr for `min_acr` (`mod_users.session_policy_factors`). The `credential_rule` is skipped only when the impersonation was started through a platform operator profile: the impersonation session's recorded acting profile (`impersonator_profile_id`) is active and is an operator profile (an operator's credentials can never be authorized for a customer party). Merely holding an operator profile is not enough: a principal that also holds a customer-party administrator profile and impersonates through it is held to every party's `credential_rule`. `min_acr` binds every impersonation. Confinement binds the parent session's factors too, for every impersonator that is not an operator by that same test: a parent factor confined to one party locks the impersonated profile (`confined`) unless it belongs to that party, so an administrator whose credential is confined to party X cannot impersonate a member of party Y; an operator impersonation is exempt, since operator credentials confined to the operator party would otherwise make operator impersonation impossible. The own arm confers only operations with `authz_operations.ownership_confers` (never `impersonate`, `manage` or `login`). The facade also exports `localAuthz.AccessFuncGenerator()` and `localAuthz.AccessRowFilter`, the list-side counterpart of this gate (see below).

**Impersonation lifecycle.** The gate rules above are the whole of what an impersonation may skip; the rest of its lifecycle is constrained as follows. The session mechanics (child session, token, renewal cap) are in [Impersonation sessions](./architecture/sessions-and-tokens.md#impersonation-sessions).

- **The impersonated actor's rules apply to every operation except stopping the impersonation.** The impersonated profile's authorizations decide what the session may do, and every party policy applies as for that profile, so impersonation never weakens a party's authentication policy. The single exemption is the `credential_rule` for an operator impersonator, keyed on the recorded acting profile (`sessions.impersonator_profile_id`) and never on the principal merely holding an operator profile; `min_acr` and step-up are evaluated on the parent session for everyone. Confinement is applied to non-operator impersonators on the same key.
- **Nested impersonation is disallowed by construction.** A database invariant (`MF101`) rejects an impersonation session whose parent is itself an impersonation, so no authorization check has to catch it and no writer can bypass it; `POST /v1/impersonations` additionally refuses a caller whose session is already an impersonation, and a profile the caller holds, with `403 users.impersonation_not_allowed`. This removes the nested identity-switch audit bug of the earlier model.
- **Credential and identification data is off limits.** An impersonating context is refused `403 users.impersonation_not_allowed` by `/v1/principals/{uuid}/credentials*` (all four routes, before the principal lookup), by `EnsurePersonalParty` and by managed-user creation (`POST /v1/parties/{party_uuid}/managed-users`, which would set a password and may authorize it for the party); the party authentication-policy writes, the party credential authorization and confinement writes, and the self-service credential writes are likewise refused with a plain `403`; so is ending a profile (`PATCH /v1/profiles/{uuid}` with `status: ended`), whose departure cleanup removes credential authorizations and revokes party-confined credentials. Separately, a caller addressing its own principal on `/v1/principals/{uuid}/credentials*` is refused `403` for every caller, service accounts included, and self-service credential changes stay on `/v1/me` (keys are rotated by their owner or an operator).
- **Planned, not built: impersonation data protection classes.** The refusals above are a fixed list in code, the immediate form of a broader rule. A general design is planned to replace them and is **not implemented**: data and fields would carry an impersonation access class, `no-write` (readable but never writable, such as a public nickname that is also an identifier), `no-read` (writable but never readable, such as personal notes, so a support operator can append a note without reading the user's) or `no-access` (neither: credentials, names, birthdates, account numbers, addresses, contact details and any other non-public identifying information). A request or function would declare which marked data it touches, and the impersonation-context check would run only when a function is about to touch marked data, so other requests pay nothing, while protected functions always perform it. An operator impersonating a user for support would then see everything the user sees except the marked data. Where the marks live (mod-core field metadata or this module), how they compose with the `AuthContext` impersonation fields and mod-authz, and whether list and read helpers need generated support are open questions; the work likely needs a mod-core change. Until it exists, the refusals above are the whole of the protection.
- **`auth_time` is inherited.** The child session copies the parent's `auth_time`, so an impersonation never looks more recently authenticated than its administrator.
- **Renew re-authorizes.** `POST /v1/impersonations/current/renew` re-checks `impersonate` on the impersonated profile from the parent session, as the recorded acting profile: a refusal revokes the child and answers `403`, and an ended parent answers `401 users.session_revoked`. The operation's `max_auth_age` is not re-applied (freshness was enforced at start); `min_acr` still binds, and the impersonation still ends at `AUTH_IMPERSONATION_MAX`.
- **Ending and logging out.** `DELETE /v1/impersonations/current` ends only the impersonation. `POST /v1/session/logout` revokes the caller's own session, which with an impersonation token is the child, so a client signing a tab out while it impersonates first restores the administrator's token and logs that session out: logout while impersonating revokes the administrator session, and with it the impersonation (`parent_revoked`), rather than leaving the administrator signed in behind a signed-out tab. Revoking or expiring the administrator session ends the impersonation on its next request either way.
- **The impersonation token is never refreshed and never replayed as the administrator.** No refresh token is issued for an impersonation. When its access token expires, a client drops it and restores the administrator's own token through the administrator's lineage; it does not retry the failed request under the administrator's token, which would run the request as the administrator instead of the impersonated profile, and it does not mint a replacement impersonation token without a renewal.

**System actors and unmarked contexts.** Exactly two kinds of context bypass the prelude's two gates (assurance and owning-party): the anonymous context (the anonymous profile holds no grants, so skipping its gates confers nothing), and a trusted system actor, a context for which `opctx.IsSystemActor` is true because it was built with mod-core's explicit marker, `opctx.WithSystemActor`. The marker is never inferred: a non-anonymous context with no session, no credential and no marker is gated and fails closed (ACR 0, no authentication time, no factors to meet a restrictive party's policy), and an impersonating context is never a system actor. Only trusted system flows may call `opctx.WithSystemActor`, never on behalf of a user's profile, and the marker is not an operator signal (the operator exemption is keyed on the acting profile, inside `mod_users.session_meets_party_policy`). mod-users has no producer of the marker. Its unauthenticated flows (sign-up, guest creation, password reset, OIDC just-in-time creation, link and step-up callbacks, bootstrap) build unmarked contexts for real users and never call `Authorize`, `AuthorizeType` or `AuthorizeTypeIn`; `api/internal/service/sessionless_contexts_test.go` pins both facts (no builder yields a system actor; no such flow reaches an `Authorize` entry point), and its static audit recognises literal-valued context fields only and follows callees within the same package.

**List-side gate.** The list functions mod-core generates (`accessible_<slug>_ids_for_actor`) apply the same owning-party gate as the prelude, so list and single-row checks agree. mod-users installs `mod_users.access_row_permitted(p_actor_entity_id, p_entity_id, p_owner_id, p_session_id, p_credential_id, p_system_actor)` as mod-core's row-filter predicate (`setup.NewRowFilterGenerator`); the six arguments are, in order, the acting profile, the candidate row, its owner, and the request's session id, credential id and system-actor flag as `setup.BindAuthInputs` bound them. It returns true for a system actor (`p_system_actor IS TRUE`), and otherwise the result of `mod_users.owning_party_gate`, the one SQL definition the single-row prelude's party check shares. That function gates the owner and, when the row is itself a `legal_entity`, the row, through `session_meets_party_policy`, which holds the operator exemption, the impersonation rules and the confinement check. NULL and false never exempt, so a call whose inputs were never bound fails closed for every row a restrictive policy gates, silently: it still lists the rows the gate does not refuse (a member of the owning party, the actor's own subject, an operator profile, an owner without a restrictive policy). There is no anonymous branch: the anonymous profile can hold no grant and join no actor group, so every arm lists nothing for it. The host obligations are to install the access functions through `localAuthz.AccessFuncGenerator()` (or wrap its own decorated generator with `setup.NewRowFilterGenerator(decorated, localAuthz.AccessRowFilter)`), and to call `setup.BindAuthInputs(ctx, tx)`, checking its error, in the transaction of every list query that joins an access function, one transaction per request context. Skipping the generator, or running a list query outside the bound transaction, breaks list and single-row parity with silently fewer rows. `ListPrincipals` (`GET /v1/principals`) runs its count, page and detail reads in one bound read-only transaction and refuses the request if the binding fails.

**Action-required responses.** Three gates emit an *action-required* response — a top-level `action` object, distinct from the `error` envelope, telling the client to navigate the user somewhere rather than surfacing an error — instead of a plain error when they block a request: the email-verification gate (`RequireVerifiedEmail`, `403 users.email_unverified`; exported for other modules' routes, not mounted on any mod-users route), the step-up gate (`409 users.step_up_required`), and the OIDC-onboarding gate (`RequireOIDCConfirmed`, `503 users.oidc_not_confirmed`, carrying `data.state`). The step-up response is raised wherever assurance or freshness falls short: an operation's `min_acr` or `max_auth_age` in the engine's prelude (the `impersonate` and `credentials` operations carry a ten-minute `max_auth_age`), a party's `min_acr`, a stale `auth_time` on a self-service write (`AUTH_SELF_SERVICE_MAX_AUTH_AGE`), and a refused step-up factor. It is the shared `apiresp` action-required error mod-core defines, so `WriteError` renders it uniformly even when it is raised inside another module's service. It also surfaces through authentication: the invite-only app gate's `login` operation (`Authenticator` with the app gate, `SessionService.gateFor`) answers `409 users.step_up_required` when the operator sets `min_acr` or `max_auth_age` on it, and the operator-admin checker of the OIDC configuration routes treats that refusal as not admitted (fail closed), falling through to the setup token. Each is written via mod-core's `apiresp.WriteActionRequired`; the three codes mod-users owns are declared once in a small internal registry, `api/internal/useraction`, rather than as inline literals at each call site.

**Request order and route authentication.** Every route answers in one fixed order: `401` (no live session or credential), `400` (stateless request shape: path UUIDs, strict JSON body, field checks), `403` (authorization), `404` (lookup), then `409`/`422` (state conflicts, only after authorization). The module-wide rules that produce it, with the wire-visible detail in the spec's [Request order and existence masking](./mod-users-spec.md#security-requirements) and the upgrade impact in [consumer-upgrade-notes.md](./consumer-upgrade-notes.md#http-error-precedence-conformance):

- **`requireAuth` is mounted by the manifest on every authenticated prefix.** `/v1/session`, `/v1/impersonations`, `/v1/me`, `/v1/principals`, `/v1/parties` and `/v1/profiles` each list `requireOIDCConfirmed` then `requireAuth` in their manifest entry, so the registrars never mount it themselves; the public and credential routes (`/v1/auth/*`, `/v1/bootstrap`, `/v1/oidc-config`) never get it. Authenticated handlers read the `auth.Identity` that `requireAuth` installs and answer `500` if they are mounted outside it, so a mis-wired host fails loudly rather than open, and a facade test mounts every authenticated registrar behind `auth.NewRequireAuth` and asserts `401` is the first rejection whatever the request looks like.
- **Stateless checks precede authorization.** Handlers decode bodies with `server.Decode`, a thin wrapper over `apiresp.DecodeJSON` that rejects unknown fields, trailing data and empty bodies and caps the body at 1 MiB, and parse path UUIDs with `apiresp.ParseUUIDParam`. Request-shape rules live in `Validate()` methods on the request types so they run before the authorizer is called. Services repeat the checks that matter to in-process callers, after authorization.
- **Existence is masked.** A principal, party or profile the caller may not read is `404`, the same as an unknown one, before any `403`; the `403` is for an operation the caller may see but not perform. See [D21](#key-decisions).
- **The step-up gate sits after the stateless checks.** On the self-service writes the `409 users.step_up_required` gate is an authorization-stage check: it runs after every `400` shape check and before authorization, so a malformed request is a `400`. On principal disable and enable and on a profile status change it runs after authorization (`read` for the `404`, then `update` for the `403`, then freshness).
- **State conflicts come after authorization.** A duplicate identifier or credential is `409` (`users.identifier_taken`, `users.ssh_key_in_use`, `users.oidc_identity_in_use`), and a transition that does not apply is `409 users.profile_transition_invalid`.
- **Documented exceptions.** Public and credential routes have no `401` gate; their credential failures are `401 users.invalid_credentials`, which does not distinguish an unknown identifier from a wrong secret. The OIDC config write routes (`confirm`, provider `POST`/`PUT`) accept the credential in the body (`setup_token`), so they check an admin bearer, then the `X-Setup-Token` header, then decode the body, then verify the body token; a caller with neither of the first two and a malformed body gets `400` before the body credential is checked. The setup token is accepted on these routes only while OIDC is unconfirmed: once OIDC is confirmed they require an operator admin session even while the bootstrap is pending, and `POST /v1/bootstrap` alone keeps the setup token live while the bootstrap is pending. `POST /v1/bootstrap` is a public route outside `requireOIDCConfirmed`: its credential is the `X-Setup-Token` header, checked before the body is read (`401 users.setup_token_invalid`, then `400`, then `409 users.already_bootstrapped`), because bootstrap may precede OIDC confirmation. `requireOIDCConfirmed` (`503 users.oidc_not_confirmed`, even ahead of `401`) answers before any handler `400` because it depends only on service state. The anti-enumeration `204` responses (email-code request, password-reset request) are unchanged.

Routes are wired into the generated server via `moduleforge.module.yaml`'s `provides.routes` entries (consumed by the ModuleForge mfgen codegen). Per-route middleware differentiation is expressed by giving the affected route prefix its own manifest entry with its own `middleware:` list — `/v1/auth` sits behind `requireOIDCConfirmed` alone, `/v1/oidc-config` and `/v1/bootstrap` behind neither, and every authenticated prefix behind `requireOIDCConfirmed` then `requireAuth` — rather than by any register-time conditional. The same manifest also wires internal service construction: `provides.services` entries build handler and service instances rather than relying on app-level startup hooks — for example, the `authenticator` service takes the `authorizer` service (`auth.NewAuthenticatorWithAppGate`), so the invite-only app gate is evaluated by the same engine as every other check, and the `anonymousActor` service resolves and verifies the anonymous system actor at boot.

Every Postgres-touching service described above is routed through the single `requires.infra: pool` singleton `moduleforge.module.yaml` declares — with one deliberate exception: `config.Load()`'s signing-key bootstrap (see [Configuration and secrets bootstrap](#configuration-and-secrets-bootstrap)) opens its own raw `pgx.Connect` against `cfg.DB.URL` from inside `Load()` itself, entirely outside the `provides.services`/`requires.infra` wiring. This is necessary, not an oversight: `Load()` is the first call in every generated `main.go`, before the pool is constructed, so it has no pool to route through yet.

## Authentication flow

Authentication is multi-channel: a user may hold credentials of several kinds, all resolving to the same principal. Every interactive sign-in creates a [session](./architecture/sessions-and-tokens.md#the-session-is-the-revocation-unit) with the signing-in credential as its first factor, lands on a profile, and answers with the token response (access token, per-tab refresh token, session, profile and the profile list). The credential kinds are described under [Principals, identifiers and credentials](#principals-identifiers-and-credentials).

**Guest user (anonymous session).** `POST /v1/auth/anonymous`, called with a `device_id` and no `device_token`, creates a *guest user* — a real, per-device principal with a personal profile, no person record and one `anon` credential — and its session, and answers `201` with the token response and a one-time `device_token`. Presenting that `device_token` on a later visit signs the same guest back in (`200`, no new token), so the guest keeps its identity and data across visits. A guest can hold only `anon` credentials and no party profile (database invariants `MF102` and `MF103`). `POST /v1/me/upgrade` upgrades the guest in place: it supplies an email, password and name, the same principal and everything it owns become a registered user, and the `anon` credential is revoked, which ends the guest's sessions, so the client signs in again with the new password. Both are refused with `403 users.byo_identity_disabled` when the platform does not allow bring-your-own identities. A guest is a different thing from the anonymous system actor described next, and the two are not converged.

**Anonymous system actor (tokenless).** A complementary but distinct mechanism: a single, well-known, zero-authority `system_actor` entity (slug `anonymous`, seeded by mod-core; see [Data model](#data-model)) that a genuinely tokenless request — no `Authorization` header at all — resolves to via the opt-in `resolveOrAnonymous` middleware, before any authorization check runs. Unlike a guest user, the anonymous actor is shared by every tokenless caller, is never persisted per-caller, owns nothing, has no credential or session, and can never hold a grant. mod-users does not mount this middleware on any of its own routes; it exists for other ModuleForge modules — e.g. one serving public, read-only resources — to compose onto their own routes. The two mechanisms compare as follows:

| | Guest user (`POST /v1/auth/anonymous`) | Anonymous system actor (`resolveOrAnonymous`) |
|---|---|---|
| Shape | Session bootstrap: one round trip, returns a token response | Tokenless: zero round trips |
| Identity | One persisted `user` principal (an `anon` credential and a personal profile) per device | One shared principal and profile for all callers |
| State | Owns things; the device token gives continuity across sessions | Owns nothing, ever |
| Upgradeable | Yes — becomes a registered user, keeps its principal and its data | No — has no credential and never will |
| Authority | A normal actor; can hold grants through its personal profile | Provably zero; holds no grants by construction |

A caller who *does* hold a valid guest token and hits an anonymous-enabled route takes the normal authenticated branch and gets its own guest actor, not the shared one.

`resolveOrAnonymous` behaves exactly like `requireAuth` except on one branch: a request whose `Authorization` header is genuinely absent falls through with the anonymous actor's principal and personal profile placed on the operation context (`AuthContext{..., Anonymous: true}`, no session, no credential, no `auth.Identity`), instead of a `401`. A header that is present but invalid, expired, malformed or not live still returns `401` — the middleware never silently downgrades a bad credential to anonymous. `auth.IsAnonymousActor(ctx)` is the accessor code uses to tell "no credential was presented" apart from "an authenticated caller, including a guest user."

It is opt-in per route group: a consuming module adds `resolveOrAnonymous` to a `scope: public` route group's `middleware:` list, with `requireOIDCConfirmed` listed first — matching every existing route entry in this module's own manifest — for example `middleware: [requireOIDCConfirmed, resolveOrAnonymous]`. That opt-in governs only whether a given route group *uses* the middleware, not whether it is *constructed*: `provides.middleware` entries are unconditional reachability roots in mfgen, so `resolveOrAnonymous` — and the `anonymousActor` service it depends on — is built at boot in every application that composes mod-users, whether or not that application's own routes reference it; mod-core's migration that seeds the anonymous actor is therefore a hard boot dependency for every mod-users consumer, not only those that adopt tokenless requests. No new `scope:` vocabulary was introduced; this rides entirely on the existing `public` scope plus the generic named-`middleware:` mechanism. `resolveOrAnonymous` must never be combined with `requireAuth` (contradictory) or `requireVerifiedEmail` on the same route group: the latter composition fails closed with a `500`, because the anonymous branch places no `auth.Identity`, which `requireVerifiedEmail` requires — a recognizable, if ugly, failure mode rather than a silent one.

Every anonymous request shares the same actor id, so actor-based rate limiting is meaningless; any route that opts into this middleware must sit behind a per-IP/CIDR rate limiter at the edge or in the composition root, and an anonymous-enabled list endpoint should enforce a hard maximum page size — mod-users documents this precondition but does not ship the limiter itself. Anonymous and authenticated responses for the same URL can differ, so any cache or CDN in front of an anonymous-enabled route must key on the `Authorization` header (`Vary: Authorization`), or the wrong response can be served to the wrong caller — consuming modules' handlers emit this header; this module's middleware does not. Because `audit_log.actor_entity_id` collapses to one value for all anonymous traffic, the per-actor audit index is useless for that id; attribution for anonymous traffic instead relies on `opctx.RequestID` plus HTTP access logs, and no module may authorize a mutating operation for the anonymous actor. A consuming module must also add its own public-visibility policy to both its decorating `Authorizer` and its list-scoping query — the generated `accessible_*_ids_for_actor` SQL function returns the empty set for the anonymous actor by design, so visibility is expressed as module-level policy, never as a grant to the shared actor.

**Local (email + password).** `POST /v1/auth/register` creates a bring-your-own user with its own `natural_person` record and personal profile, the primary email identifier (unverified), a password credential bound to it, and the session, then emails a verification code. `POST /v1/auth/login` verifies the argon2id hash and returns the token response; every credential failure is `401 users.invalid_credentials`, which does not distinguish an unknown email from a wrong password. `POST /v1/auth/password-reset/request` and `/confirm` reset a password with an emailed single-use token: confirming supersedes the password bound to the token's identifier, which also revokes every session holding it, and does not sign in.

**Email one-time code.** `POST /v1/auth/email-code/request` dispatches a short-lived code; `POST /v1/auth/email-code/verify` exchanges the code for the token response. Verifying an email identifier (`POST /v1/me/identifiers/{uuid}/verify`) automatically creates an `email_otp` credential bound to it, so passwordless sign-in keeps working; the user may revoke it. Limits: each code allows at most 5 verification attempts (a failed-attempt counter is claimed before the code is compared, and the final claim consumes the code); a new code request is subject to a 60 s cooldown measured from the newest challenge of the same kind and subject in any state (live, exhausted, or consumed), enforced atomically by the `create_challenge_with_cooldown` database function; and a code is single-use. A wrong, unknown-email, missing-code, or exhausted-code verification all answer the same `401` and spend equivalent bcrypt time, so lockout is not observable; the request endpoint always answers `204` after a ~200 ms floor, including when the request is skipped by the cooldown. The send itself runs in a detached background goroutine bounded by a per-handler concurrency limit (16 concurrent sends; excess requests are dropped with a warning log, still answering `204`), a 20 s timeout, and panic recovery, so a flood of requests cannot spawn unbounded work and a panic cannot crash the process. **Accepted residual risk (documented trade-off).** A code lives 5 minutes and the 60 s cooldown permits up to about 5 live codes per (subject, kind), each with its own 5-attempt budget. That gives roughly 5 guesses per minute per account against a 10^6 code space, with no per-IP or per-account lockout. Separately, an attacker who knows an email can exhaust the newest code with 5 wrong guesses, so the victim cannot obtain a fresh code for up to 60 seconds (the cooldown counts exhausted codes), and can repeat this each minute. Mitigations considered but out of scope: a per-(subject, kind) failed-attempt window across all live codes, and per-IP throttling on the public verify endpoint.

**Step-up.** Step-up is not a separate token: it adds or re-verifies a factor in the current session, recomputes `acr`, resets `auth_time` and returns a fresh access token (`POST /v1/session/step-up/password`, `.../email-code/request` and `.../verify`, `.../oidc/{provider}/start`). The emailed step-up code is a `step_up` challenge bound to the session and enforces the same limits as above. See [Step-up](./architecture/sessions-and-tokens.md#step-up).

**OIDC (Google, Microsoft, Authelia, and others).** The OIDC flow is:
1. Client generates a random verifier and calls `GET /v1/auth/oidc/{provider}/start?handoff_challenge=<base64url SHA-256 of the verifier>` → API carries the challenge in the signed state, sets the `oidc_state` cookie and redirects to the authorization URL. The callback's one-time handoff code is redeemable at `POST /v1/auth/handoff` only with that verifier.
2. User authenticates at the IdP. IdP redirects to `GET /v1/auth/oidc/{provider}/callback`.
3. API exchanges the code for an id_token, validates it with `go-oidc`, and extracts the issuer, `sub` and the claims it needs.
4. API resolves the verified `(issuer, subject)` against active `oidc` credentials, and **never links an identity by email**.
   - Match found → create the session and a handoff code for the credential's principal.
   - No match, and the provider allows just-in-time creation (`jit_mode`): `byo` creates a bring-your-own user with its own person record and personal profile; `managed` creates a user managed by the provider's party; the new user's `oidc` credential is created with the same primitive the trusted link helper uses.
   - No match, `jit_mode` `none`, or an email that already belongs to an existing user → the callback redirects with `#error=no_account` or `#error=account_exists_sign_in_and_link`: the person signs in another way and links the provider from their account (`POST /v1/me/credentials/oidc/{provider}/start`, which links the verified identity as an `oidc` credential of the calling session's principal).
5. The callback redirects with `#handoff=<code>`; no token or refresh token is ever placed in a URL. The handoff exchange is described in [The OIDC handoff code](./architecture/sessions-and-tokens.md#the-oidc-handoff-code).

**Party confinement of linked credentials.** A provider bound to a party (its `party_id` is set) confines every OIDC credential created through it to that party: just-in-time managed-user creation and the authenticated link callback both set the credential's `confined_to_party_id` to the provider's party. A confined credential authenticates only that party's profiles. A provider with no party links unconfined credentials.

Provider configuration is loaded from environment variables (`AUTH_PROVIDER_<PROVIDER>_CLIENT_ID` / `_CLIENT_SECRET`) and can be overridden by rows in the `oidc_providers` table. In local dev, Authelia acts as the default IdP and is wired automatically by Docker Compose.

OIDC issuer discovery and JWKS fetches verify the issuer's TLS certificate by default. Skipping verification requires the explicit, local-development-only `WithInsecureSkipTLSVerify()` verifier option (passed to `NewVerifierWithOptions` alongside `WithOIDC`), which applies only to an `https://` issuer and logs a warning naming the issuer host. Consumer migration steps are in [docs/consumer-upgrade-notes.md](./consumer-upgrade-notes.md#oidc-issuer-tls-verification).

For OIDC configuration issues and troubleshooting, see [docs/oidc-troubleshooting.md](./oidc-troubleshooting.md).

**SSH public key (git-over-SSH access).** A standing, non-interactive credential, distinct in kind from the session-oriented channels above: `POST /v1/me/credentials/ssh-keys` (or, for an administrator acting on another principal, `POST /v1/principals/{uuid}/credentials/ssh-keys`) registers an `authorized_keys`-format public key as an `ssh_key` credential of a principal, subject to a fixed algorithm-acceptance policy (see [docs/mod-users-spec.md](./mod-users-spec.md#security-requirements)). It is used by a composing application's own SSH transport (for example `app-mfgit`/`mod-repos`), not by this module's own HTTP API. A registered key resolves to the credential and its principal via the `sshKeyResolver` service exported for that purpose (see [API layer](#api-layer) and [Key decisions](#key-decisions)), and `AuthContextForOwner` derives the `AuthContext` the repository operation runs as: the principal's active profile in the repository's owning party when it has one and the credential is available to it, else the personal profile unless the credential is confined to a party, and never a profile the party's authentication policy locks the key out of (the key counts as a possession credential at its kind's base assurance, and can never satisfy a rule that requires an OIDC provider). Revocation revokes the credential and takes effect on the caller's very next SSH connection; an already-open session is not terminated. The anonymous system actor can never authenticate over SSH: a system actor holds no credential.

**The invite-only app gate.** A session can be started for an app. When the app is `invite_only` (a mod-core column), starting or continuing a session requires the acting profile to be granted the `login` operation on the app's entity, evaluated by the same authorization engine as every other check (wildcard, entity, owned-scope and actor-group arms) rather than a second mechanism. A refusal is `403 users.app_login_not_granted`; a `min_acr` or `max_auth_age` set on `login` surfaces as `409 users.step_up_required`. A party restricts its members to specific apps by granting `login` to a group.

## Principals, identifiers and credentials

A **principal** is who authenticates: a `user` (a human, with a session), a `service_account` (a machine, with non-interactive credentials and client-credentials tokens, never a session) or a `system_actor` (trusted platform code, which never authenticates). A principal always acts through a **profile**, and the profile, not the principal, is the subject of every authorization check.

**Users.** A user is either *bring-your-own* (it owns itself, has exactly one personal profile, and may hold party profiles in any party) or *managed* (owned and managed by a party, no personal profile, party profiles only in that party), or a *guest* (a device-bound anonymous user with only the personal profile). A user's name lives on its own `natural_person` record (`users.person_id`), created at registration, guest upgrade and just-in-time OIDC creation and owned by the user, so the user's personal profile reaches its own legal record through the own arm without an extra grant; managed users get no person record by default. A managed user's credentials are party-controlled.

**Identifiers** (`user_identifiers`) are how a person is addressed, not evidence of who they are: an email (and phone and username kinds) with a verified flag and one primary. `UNIQUE (kind, value_canon)` keeps one account per canonical address, including addresses a person has not yet proven they hold. Only **credentials** are evidence: verifying an email never logs anyone in by itself, and an OIDC login is never matched to an account by email.

**Credentials** are the means of proving a principal's identity, one row per credential with a per-kind subtable:

- `password` — an argon2id hash, optionally bound to an identifier (at most one active password per identifier and one unbound password per user);
- `email_otp` — passwordless sign-in through a verified email identifier;
- `oidc` — an `(issuer, subject)` pair from a configured provider, unique among active credentials;
- `ssh_key` — a public key (git-over-SSH; see [ssh-keys.md](./architecture/ssh-keys.md)), unique by fingerprint among active credentials;
- `api_key` — a `client_id` and a hashed secret for a service account's client-credentials grant;
- `anon` — a guest's hashed device token.

A credential carries an optional `default_profile_id` (where a sign-in with it lands), an optional `confined_to_party_id`, an expiry and a revocation. Credentials are never deleted; revoking one (`revoked_at`, with a reason) ends every session that holds it as a factor. Guests, service accounts and system actors are limited to the kinds their type allows by the database (`MF102`). The credential kinds registry and the assurance each provides are in [Assurance](./architecture/sessions-and-tokens.md#assurance-acr-amr-and-auth_time).

**Profiles and parties.** A **profile** is a principal's seat in a **party** (an organization or a natural person; mod-core's `legal_entity`) or its personal profile. A user holds one personal profile and any number of party profiles (`invited`, `active`, `suspended`, `ended`); a party invites a user (`POST /v1/parties/{party_uuid}/profiles`), which the user accepts or declines (`/v1/me/profiles/{uuid}/accept`, `/decline`), and a holder can leave. Ending a profile runs a departure cleanup: the holder's credential authorizations for the party are deleted, their credentials confined to the party are revoked (which ends the sessions holding them), and a managed user left with no open profile is disabled. A natural person who wants a team plan gets a personal party idempotently (`EnsurePersonalParty`), together with an owned-scope `manage` grant held by their personal profile over everything the person party owns, but never over the person record itself.

**Party authentication policies.** A party sets how its members must authenticate through `party_authn_policies` (`GET`/`PUT /v1/parties/{party_uuid}/authn-policy`): a `credential_rule` of `any`, `authorized` (a factor must be one the party has authorized, or one confined to it) or `provider` (a factor must come from the party's required OIDC provider), and a `min_acr`. A party administrator, or a credential's own holder acting through a session that meets the party's gate through another factor (so a credential never authorizes itself), authorizes credentials (`credential_party_authorizations`) and confines them. The policy is enforced continuously: it decides which of the party's profiles a session can act as, and the authorization engine applies it again to outside actors who reach the party's content. A party also admits **outside collaborators** (profiles outside the party added to its actor groups or named in its grants): mod-authz consults the `CollaboratorGate` hook this module provides, inside its own write transaction, and a collaborator whose credentials cannot meet the party's policy needs an explicit confirmation from someone holding `update` on the party; a confirmation exempts the `credential_rule` only, never `min_acr`.

When a new OIDC login arrives for an identity already linked to a principal, it signs that principal in; an email that matches an existing user never links by itself. This keeps a person who originally registered with email and password from being captured by whoever controls a matching address at an identity provider.

## GUI component library

`gui/` is a React component library built with tsup and exported as `@moduleforge/users-gui`. It provides ready-made auth UI: `LoginForm` (email/password login, plus OIDC-provider sign-in buttons when the API reports configured providers) and `RegisterForm`, both self-contained components that call `useAuth()`/the API client directly, and five full-page compositions — `AuthPage` (composes both forms behind an in-page login/register mode toggle), `OidcCallbackPage` (handles the OIDC provider's redirect-back leg), `ForgotPasswordPage` (requests a password-reset link, then shows an in-place confirmation view), `ResetPasswordPage` (sets a new password given a reset token passed in as a required prop — it never reads the URL or a router itself), and `EmailCodePage` (passwordless sign-in via an emailed one-time code, toggling between an internal request/verify step) — which report outcomes via router-agnostic callback props rather than performing navigation themselves. `ForgotPasswordPage` and `ResetPasswordPage` call the API client directly (unlike `LoginForm`/`RegisterForm`, which call `useAuth()`'s `login()`/`register()`); `EmailCodePage` additionally calls `useAuth()` to establish the session once a code is verified, like `LoginForm`'s own use of `useAuth()`. The account self-service panels are additional components, not full-page compositions, meant to be embedded in a host's own settings pages: `CredentialsPanel` (lists, adds, edits and revokes the caller's credentials on `/v1/me/credentials`; SSH keys are one credential kind; for a guest it shows `GuestUpgradeForm`), `IdentifiersPanel` (email identifiers on `/v1/me/identifiers`) and `SessionsPanel` (live sessions on `/v1/me/sessions`, signing the tab out when the current one is revoked). They call only the shared `api` client singleton for the runtime base URL, with no base-URL prop or env read of their own. A `409 users.step_up_required` is not handled inside a panel: `StepUpDialog`, mounted once under `AuthProvider`, registers as the step-up handler and prompts for the password, an emailed code or an OIDC provider, then the client retries the interrupted request once with the fresh access token; no step-up token is held anywhere. For every other action-required response (notably `users.email_unverified`) a panel shows an inline alert and invokes the optional `onActionRequired` callback. Source layout: `src/components/` (UI components), `src/lib/` (API client, runtime configuration, return-path safety, standard routes, utilities). The `tsup` build emits JS and type declarations only — no CSS is bundled into `dist/`, and `gui/package.json` exports only the package root (there is no `./styles.css` export). The Tailwind v4 entry stylesheet lives at `.ladle/styles.css` and is used only by the Ladle component workbench (`make preview`); consumers generate their own CSS via Tailwind v4 `@source` scanning of the library's built `dist/` output, as `app-mfdemo` does. The client implements the Bearer-only, per-tab frontend contract: tokens live per tab in `sessionStorage` (never `localStorage` or a cookie), and every request carries `Authorization: Bearer` with `credentials: 'omit'`, except the two OIDC authorize-URL start POSTs (link and step-up), which send `credentials: 'include'` so the signed `oidc_state` cookie that the redirect callback validates is kept; see [Client contract](./architecture/sessions-and-tokens.md#client-contract).

**Runtime configuration and the 401 seam.** `src/lib/config.ts` is the single home for process-wide client settings, set once by the host app through `configureUsersApi` (base URL, token storage key, unauthenticated redirect URL, optional return-path query parameter, and an `onUnauthenticated` handler); the fetch layer in `src/lib/api.ts` reads them lazily on every request, so there is no import-order dependency. When an authenticated request returns `401`, the client first tries one token refresh through the tab's refresh lineage and replays the request; when the session cannot be repaired (no refresh token, a revoked or reused lineage, or a replay that still fails) it clears the tab's tokens and then either runs the configured `onUnauthenticated` handler or hard-redirects via `window.location` (default `/auth/login`); the request still rejects with `ApiRequestError`, even when a handler throws (the throw is caught and logged). Credential-failure `401`s — login, email-code verification, password reset, and email verification — pass `skipAuthRedirect` and surface as inline form errors rather than session expiry. The base-URL environment/`window` fallbacks are trusted deploy-time inputs and are not validated; only values passed to `configureUsersApi` are. Return paths written by the 401 handler and read by `readReturnPath()` share one predicate, `isSafeReturnPath` (defined in `config.ts`, re-exported from `src/lib/return-path.ts` and the package root), and local-login return handling is opt-in via `unauthenticatedReturnParam`. `AuthProvider` complements the fetch-layer redirect with a router-agnostic soft navigation through its `onNavigate`/`loginPath` props. Field-level detail lives in [`gui/README.md`](../gui/README.md#runtime-configuration) and [Unauthenticated handling](../gui/README.md#unauthenticated-handling).

**Standard screens and the backend-to-path contract.** The library still owns no route files and never reads a router, but beyond the five compositions above it ships page components for the paths the backend fixes and exports the standard path set as `USERS_GUI_ROUTES` (`src/lib/routes.ts`). An action-required response (see [API layer](#api-layer) above) reaches the client as `ApiActionRequiredError` carrying the envelope's `path`; `AuthProvider` handles it on its own calls by keeping the session intact and navigating via `onNavigate(err.path)` (skipping a navigation to the exact pathname the browser is already on). The mapping is: `users.email_unverified` -> `/verify-email` -> `VerifyEmailPage` (a six-digit emailed-code flow), and `users.oidc_not_confirmed` -> `/oidc-config` -> `OidcConfigPage` (dual-mode: setup-token for an operator with no session, admin reconfiguration for a signed-in admin), with `OidcSetupGate` (migrated from `app-mfdemo`, behavior-preserving, alongside `OidcConfigPage` and its provider add/edit modals) probing OIDC status so an unconfirmed deployment routes to the config page. `/reset-password` is likewise backend-fixed (the reset email links there) and served by `ResetPasswordPage`. `users.step_up_required` -> `/step-up` has **no page yet**: the library does not mount it and `AuthProvider` has no step-up navigation. The consuming app creates the routes and mounts these components; see [Routes](../gui/README.md#routes) and [Standard pages](../gui/README.md#standard-pages) for the table, props, and Next.js/React Router examples.

The library depends on `@moduleforge/core-gui` as a peer. This dependency resolves through a bun workspace rather than a published registry: this repo's root `package.json` declares `"workspaces": ["gui", "../mod-core/gui"]`, so `bun install` at the repo root links the sibling repo's `mod-core/gui` in directly (requires `mod-core` checked out alongside this repo). `mod-core/gui` must be built once before `gui/`'s own build/typecheck resolves it. See [AGENTS.md](../AGENTS.md) for the setup procedure.

The `app-mfdemo` project (a separate Next.js app at the aggregate level — not part of this Bun workspace) wires together the running API and the GUI components to demonstrate a complete integration. It serves as the component showcase in lieu of a dedicated story tool.

## Lock order

Transactions that lock more than one of the rows below take them in this order, so concurrent writers wait instead of deadlocking (Postgres breaks a cycle with SQLSTATE 40P01, a 500 for the caller). The order is read off the code, not a convention enforced by the database. One exception to the numbering: a profile status transition holds the profile row (3) before it takes `platform_settings` (1), see item 3.

1. **`platform_settings`** (the singleton row, `FOR UPDATE`), for transitions that can remove an operator administrator: `requireNotLastOperatorAdmin` (`profile_last_admin.go`, called from `transitionLocked`, so ending, suspension and leaving all take it) and `requireNotLastOperatorAdminForDisable` (the principal-disable path, `disablePrincipalInTx`), which locks it before the principal row. Bootstrap locks it first of all. Neither guard locks a row when the party is not the operator party or the principal holds no active operator-party profile.
2. **The users row** (`FOR UPDATE`, e.g. `resolveInvitee` when inviting).
3. **The profile row** (`lockProfile`, `FOR UPDATE`, mod-core's generated `dblock` row lock). A profile status transition (`EndInTx`, the admin status update, the holder leave) locks the profile first and then takes `platform_settings` inside `transitionLocked`; this is consistent with the disable path because disabling a principal takes `platform_settings` and the principal row but never locks a profile row.
4. **The credential row** (`FOR UPDATE`). Credential writes gated by `gateCredentialWrite` take the holder's profile `FOR SHARE` first and then the credential, matching the profile-then-credential order of `EndInTx` and the departure cleanup that revokes the holder's party-confined credentials; the reverse order would be a lock cycle.
5. **The party policy**, taken before the policy row it covers: the per-party advisory lock (`lockPartyPolicyExclusive` for `PutAuthnPolicy`, `lockPartyPolicyShared` for the confirmation writers: invitation, managed-user provisioning and `CollaboratorGate`), then the `party_authn_policies` row `FOR UPDATE` or `FOR SHARE`. The advisory lock stands in for the row while the party has none. Both release at the end of the transaction.

Bootstrap takes `platform_settings` and then only creates rows (the first user, the operator organization, created through mod-core's trusted `OrganizationService.CreateInTx` in the bootstrap's transaction, and the admin profile); it never locks an existing profile after taking `platform_settings`, so it cannot invert the profile-then-`platform_settings` order of a transition.

## Key decisions

- **D1 — Schema placement.** Every table, function and trigger this module owns lives in the `mod_users` schema and is referenced schema-qualified; platform-canonical tables (`entities`, `types`, `principals`, `profiles`) stay in mod-core's `public`. This replaces the earlier mixed layout (older tables unqualified in `public`, SSH keys alone in `mod_users`): the baseline was being rewritten for the identity model anyway and no backward compatibility is required, so one rule ("every mod-users table is `mod_users.*`") replaced the exception. A composing host's provisioning must grant `USAGE` on `mod_users` plus table privileges (the migration issues no `GRANT`), and `public`-scoped backup/reset/test tooling will miss the tables. See [Data model](#data-model) and [D1](./architecture/ssh-keys.md#d1-schema-placement) for the rationale and the full privilege sets.
- **D2 — Global fingerprint uniqueness.** A key resolves to at most one active credential, enforced by a partial unique index in the schema (`cred_ssh_key_active_fingerprint_uq`, over the `active` flag a trigger keeps in step with `revoked_at`), not a Go pre-check — a Go-only check would lose a concurrent-registration race. See [D2](./architecture/ssh-keys.md#d2-global-uniqueness-enforced-in-the-schema).
- **D3 — Revoke, never delete.** Revoking a credential sets `revoked_at` and a reason; credentials, SSH keys included, are never deleted, because other modules may reference them and a revoked row is evidence. Every read and the resolver filter on the active flag. See [D3](./architecture/ssh-keys.md#d3-revoke-never-delete).
- **D4 — No cache, immediate revocation.** The resolver issues a fresh, indexed query on every call and caches nothing at any layer, so a revocation takes effect on the very next connection. See [D4](./architecture/ssh-keys.md#d4-no-cache-immediate-revocation).
- **D9 — SSH keys are credentials, administered under the `credentials` operation.** An SSH key is an `ssh_key` credential of a principal, not a table of its own. Managing credentials, SSH keys included, is the `credentials` operation (`ownership_confers` true, `max_auth_age` 10 minutes) on the principal entity, under `/v1/principals/{uuid}/credentials*` (list, issue an API key, install an SSH key, revoke); a user manages their own keys on `/v1/me/credentials`. The generic `update` operation does not confer it, nor does `impersonate` (which is about acting as a profile); `manage` does because it implies `credentials`. Installing a key grants git-over-SSH access as the principal, so it needs fresh authentication, which `max_auth_age` enforces as a `409 users.step_up_required`. The own arm confers `credentials` on the principal's own entity, so a personal profile whose holder owns a service account can rotate its key. The earlier routes `/v1/user-accounts/{uuid}/ssh-keys*` and `/v1/self/ssh-keys*` are removed. See [D9](./architecture/ssh-keys.md#d9-credentials-operation-and-profile-derivation) for the rationale and the own-principal refusal.
- **D11 — Resolver consumer contract.** `usersservice.SSHKeyResolver.ResolveCredential` (key to credential) and `AuthContextForOwner` (credential and repository owner to `AuthContext`) are the Go shapes a composing application's transport adapts into `mod-repos`' `transport.KeyResolver`; both are pre-authentication, side-effect-free, and uncached by design, and their consumer must rate-limit handshakes and cap candidate keys per connection. See [D11](./architecture/ssh-keys.md#d11-resolver-consumer-contract).
- **D12 — Type-level authorization is distinct from entity-level.** `Authorize`'s target is always an `entities.id`; a `types.id` passed there is matched against unrelated entities, so an actor who owns, or holds a grant over, the entity whose id happens to equal the type id would pass a type-level check. Type-level `create` and `list` therefore go through `(*Authorizer).AuthorizeType(ctx, operation, typeID)` (exported as `localAuthz.TypeAuthorizer`), which never consults ownership or entity-level authority. Every type has its own entity (`types.entity_id`, from mod-core), and `AuthorizeType` allows on either of two grounds: a wildcard grant (`target_id IS NULL`), or a grant on the exact type's entity, looked up through `types.entity_id` for `typeID`, held directly or through target-group membership, by the actor or any actor group in its chain. There is no ownership arm and no subtype or parent-type inheritance, so a grant on the `legal_entity` type's entity does not cover `natural_person`. An unknown type id is denied, `typeID <= 0` fails closed even for a wildcard holder, and deprecation is not consulted (mod-core rejects creating an entity of a deprecated type at the data layer, and a deprecated type stays listable). A grant on an unrelated entity whose id equals the type id confers nothing, because `typeID` is compared only with `types.id`, never with `entities.id` or `grants.target_id`. Target groups used for type grants can hold only type entities, never a mix of type and non-type entities; that kind rule is enforced by mod-authz and documented in [mod-authz's AGENTS.md](https://github.com/moduleforge/mod-authz/blob/main/AGENTS.md). Consumers holding a `coreAuthz.Authorizer` assert `TypeAuthorizer` and otherwise fall back to `Authorize(ctx, op, nil)` (the core contract's "no specific target", wildcard-only here), **never** to `&typeID`; because that nil-target fallback is wildcard-only, it denies type-grant holders (fail closed), so a type grant takes effect only through an implementation that provides `TypeAuthorizer`. Create and list checks scoped to an owner use the owner-scoped form, `AuthorizeTypeIn(ctx, operation, typeID, ownerID)`, which admits a wildcard grant, a grant on the exact type's entity, an owned-scope grant on the owner whose type matches, and the own arm. Inviting a profile into a party (`create` on `profile` in the party) and creating a managed user (`create` on `user` in the party) use it; listing principals runs through the generated access function instead (see [API layer](#api-layer)). Rollout consideration: a `manage` grant on a type entity also confers update, delete and grant on that type entity and the ability to delegate, and, because a type grant also reaches every instance of the type (see [D13](#key-decisions)), full control of every instance of that type. Create-only authority should therefore be granted with the `create` operation (and `list` for listing), never `manage`. Grants already targeting a type's entity for other purposes now take effect for `create` and `list`, and for the instance-wide access described in D13. mod-core's `Authorizer` interface was deliberately left unchanged so every existing implementation and decorator stays source-compatible, which is why the capability is an optional assertion rather than a new interface method. This decision is recorded here only; it has no counterpart in [docs/architecture/ssh-keys.md](./architecture/ssh-keys.md).

  > **Warning: a type-level `list` grant on a type lists every instance of that type.** The search behind `GET /v1/principals` is scoped per row only by the access function's grant arms and the owning-party gate.
  >
  > - A type-level `list` grant on the `user` type's entity (or `manage`, which implies `list`) lets its holder list **every** user, including each user's primary email address, except rows owned by a party whose authentication policy the holder's session does not meet.
  > - The check is **exact-type**: a grant on a parent type's entity, or on a single instance, does not authorize listing the type.
  > - Grant `list` or `manage` on `user`'s type entity only to principals trusted with every user's email address.
  > - The same grant also confers `read` on every user instance (`list` implies `read`); see the warning in [D13](#key-decisions) rather than restated here.

- **D13 — Type grants confer instance access.** Entity-level `Authorize` honours type grants over instances: a grant on a type's entity (the entity named by `types.entity_id`) also confers the same operation over every existing and future instance of exactly that type, for every operation in the grant's `SatisfiedBy` closure. The match is on the exact type only: a grant on `legal_entity`'s entity does not reach a `natural_person`, and a grant on a subtype's entity does not reach its parent type's instances. It works through target groups (a grant on a type-only target group containing the type's entity confers the instance access for every type in the group) and through actor groups (a grant held by any group in the actor's chain). It is never applied to type entities themselves: a grant on the sentinel `type` entity confers nothing over type entities, which would otherwise let its holder derive authority over every type. The ownership arm and `AuthorizeType` are unchanged; in particular an instance grant never satisfies a type-level check, so type-level `create` and `list` still require a wildcard grant or a grant on the exact type's entity.

  > **Warning: a type grant is an instance-wide grant.**
  >
  > - A grant on a type entity confers the operation over **every existing and future instance** of exactly that type, for every operation in its closure. `manage` on a type entity is full control (read, update, delete, `impersonate`, `grant`, `revoke`, ...) of every instance.
  > - For the `user` type entity, `manage` therefore confers `credentials` over every user: installing and revoking SSH keys and issuing API keys through `/v1/principals/{uuid}/credentials*` (see D9), disabling and enabling any user, and reading every user. The credentials authenticate as that principal, but a party's authentication policy still decides which of the principal's party profiles they can reach (an installed key is not authorized for a restrictive party until that party's administrator authorizes it).
  > - Credential administration requires `credentials`: `update` on the `user` type entity does not confer the ability to install or revoke a credential. `manage` still does (it implies `credentials`), as does a direct or type-level `credentials` grant.
  > - For the `profile` type entity, `manage` or `impersonate` confers `impersonate` of every profile of that type, which is the platform's support power; the own arm never confers it.
  > - `manage`, `grant` or `update` on the type entity of `authz_actor_group` or `authz_target_group` confers that operation over every group of that kind. Adding a member needs `grant` on the member (and, for actor groups, `update` and `grant` on the group); a bare type-level `update` only permits removing members, and `manage` confers all of it. Such a holder can edit groups that hold wildcard grants, a path to privilege escalation.
  > - The same applies to every other type that has instances (`app`, `system_actor` and the anonymous system actor, an instance of `system_actor`, where they exist).
  > - `list` implies `read`, so a type-level `list` grant also reads every instance of the type.
  > - `manage` or `grant` on a type-only target group confers all of the above for every type in the group.
  > - It does not extend to subtypes or parent types, and it never applies to type entities themselves.
  > - A holder of `grant` on a type entity can hand out instance-wide authority over that type. Grant on type entities only to principals trusted with every instance, and prefer `create` and `list` for create-only or list-only authority.
  > - Single-row `Authorize` and the list-side `accessible_*_ids_for_actor` functions agree for type-grant holders: mod-core's `GrantTableGenerator` carries the matching arm, and `TestInteg_OwnerPredicate_ListSingleRowSymmetry` asserts the agreement against the production `Authorizer`.

  The `localAuthz.Authorizer` doc comment carries a short form of this warning.

- **D14 — Access tokens are EdDSA only, and the verifier pins the algorithm.** The carrier is an Ed25519-signed JWT; HS256 session tokens and `JWT_ALG` are removed, because offline verifiers (a token relay, managed apps) need public-key verification and keeping HS256 would keep the algorithm-confusion surface for no benefit. `Verifier.verifyLocal` never lets the token header choose the algorithm: only `EdDSA` is accepted, against the configured public keys, and every other `alg` (including `HS256` and `none`) is rejected before any signature check. A verify-only service therefore cannot be tricked into HMAC-verifying a token keyed with the public key bytes (algorithm confusion). The signing key is `JWT_SIGNING_KEY`, or, when unset, a key persisted in `mod_users.auth_signing_keys` so zero-config local development keeps working. See [jwt-eddsa.md](./jwt-eddsa.md#verification-behavior).
- **D15 — `kid` rotation uses a map.** Public keys are held as a `kid` to key map (`JWT_VERIFY_PUBLIC_KEYS`, `WithEd25519PublicKeys`), and a token's `kid` must match a configured entry exactly; an unknown or non-string `kid` is rejected, and a token with no `kid` matches only the key configured under the empty `kid`. Several keys are valid at once, which is what lets a new key be deployed to every verifier before the issuer switches and the old one be dropped later, with removal as the revocation mechanism. See [jwt-eddsa.md](./jwt-eddsa.md#rotation-procedure).
- **D16 — Email verification is derived from identifiers and always present.** Whether a user's email is verified is not a column of the user: it is true when the user holds at least one verified email identifier. The `email_verified` boolean is snake_case on the wire and always present on the user view, and `auth.Identity.EmailVerified` carries the same flag from the per-request liveness round trip, so the verify-email gate costs no extra query and a client needs no follow-up call after sign-in to learn it.
- **D17 — Only access tokens use the asymmetric key; the OAuth state stays HMAC.** The OAuth `state` parameter of the OIDC flow is signed with an HMAC key, `JWT_SECRET` when set and otherwise derived from the signing key (D19). An explicit secret is never accepted as an access-token verification key. The step-up token and its replay cache of the earlier model are gone: step-up is a session factor (D26).
- **D18 — CORS fails closed.** With no explicit allow-list the API emits no CORS headers outside `DEPLOY_MODE=local`; credentials are sent only with an explicit list and never with a wildcard; and `*` or any `*` pattern is rejected at startup outside local mode (the CORS library treats every entry containing `*` as a prefix/suffix pattern). `server.New` repeats the check and denies if a hand-built config reaches it, so an ambiguous configuration degrades to blocked requests rather than to credentialed cross-origin access. See [cors.md](./cors.md).
- **D19 — The OAuth state key is derived when `JWT_SECRET` is unset.** `JWT_SECRET` is optional. Precedence: an explicit `JWT_SECRET` always wins (kept as-is, no length policy change); otherwise the HMAC key is derived from the Ed25519 signing key with HKDF-SHA256 (RFC 5869; input keying material is the key's 32-byte seed, no salt, 32-byte output), using the purpose label `mod-users/v1/oauth-state` as the HKDF info input. The label is a domain-separation context: a key derived under another label is independent. The `v1` segment versions the derivation: any change that alters output must bump it, and a known-answer test pins the current value. The JWT `kid` is deliberately not mixed in. Rotation: the derived key follows the signing key, so swapping `JWT_SIGNING_KEY` invalidates in-flight OAuth state; the window equals the state lifetime and affected users simply restart the OIDC login; an explicit `JWT_SECRET` gives continuity across a signing-key swap. The resolver is `auth.OAuthStateKey`. See [jwt-eddsa.md](./jwt-eddsa.md#derived-oauth-state-key).
- **D20 — HTTP error precedence is a module-wide rule.** Responses follow `401`, `400`, `403`, `404`, then `409`/`422`, as set out in [API layer](#api-layer); the normative rule is the ecosystem's `http-error-precedence` standard. Three choices carry the weight. (1) `requireAuth` is mounted by the manifest on every authenticated prefix and never on a public or credential one, and authenticated handlers answer `500` when they find no `Identity`, so a mis-wired mount fails loudly instead of skipping the `401` gate while a public or credential route can never grow one. (2) Stateless validation, including strict body decoding, runs in the handler before any authorizer call; a state-dependent step-up check and every lookup follow it. (3) Exceptions are few and recorded: credential-in-body routes (`400` may precede the body credential's `401`), `POST /v1/bootstrap` (a public route outside `requireOIDCConfirmed` whose credential is the `X-Setup-Token` header, since bootstrap may precede OIDC confirmation), and the caller-state middleware gate `requireOIDCConfirmed`, which answers before any handler `400` because it depends only on service state. The step-up gate's placement is also the reason an SSH key is parsed in the request validation (and again in the service for in-process callers) before the authorizer is consulted. See [D9](./architecture/ssh-keys.md#d9-credentials-operation-and-profile-derivation) for the SSH-key credential routes.
- **D21 — Existence is masked behind a read check.** A principal, party or profile the caller may not read is a `404`, indistinguishable from one that does not exist, and the `403` is reserved for an operation the caller may see but not perform. The services authorize `read` first and map a plain refusal to `404` (`authorizeMasked`, `maskForbidden`), then authorize the operation itself, so an action-required refusal (a step-up) is never masked and a caller who cannot read the row never learns whether it exists. For the credential routes the order is `401`, `400`, `403` (impersonating), `404` (unknown principal), `403` (the caller's own principal), `404` (a principal the caller cannot read), `403` (`credentials` refused), then `409`. The masking costs one extra authorizer call per request, and audit trails show it. A consumer supplying its own `Authorizer` must treat the read check as an ordinary denial.

- **D22 — Party-policy gates and confirmations.** (1) *Two-door credential write:* writing a credential for a party (authorize, confine, unconfine) is allowed to a party administrator (`update` on the party) or to the credential's own holder acting through a session that satisfies the party's gate through another factor, so a credential never authorizes itself; anyone else is refused (404 when the party is unreadable, 403 otherwise). (2) *Leave is gated on `profile_gate`:* a holder leaving a party must have a session that meets the party gate (`mod_users.profile_gate`, which ignores the profile's own status), while accepting or declining an invitation stays open to a locked session. (3) *Confirmations are voided by a policy change:* `PutAuthnPolicy` deletes the party's policy confirmations when `credential_rule` or the required OIDC provider changes; a write that leaves both unchanged keeps them. A confirmation exempts `credential_rule` only, never `min_acr`. (4) *Invite-time `authorized` semantics:* when a holder is invited, the `authorized` rule counts as met by any usable interactive credential, because no credential can be authorized before the profile exists; outside collaborators are excluded from this relaxation and need an authorized or confined credential (the strict mode). (5) Confirming a mismatch (on an invitation or an outside-collaborator add) requires `update` on the party. See [Lock order](#lock-order) for the locks these writes take.

- **D23 — Liveness is checked once per request, in the authentication middleware.** `mod_users.session_liveness` (or `credential_liveness`) runs in one SQL round trip per request and also enforces profile availability (confinement, party gate, party `min_acr`); the `Authorizer` then trusts the installed `AuthContext` and enforces only the operation-level gate (`min_acr`, `max_auth_age`) and the owning-party gate. One query per request gives zero revocation latency, while repeating the check inside every `Authorize` call would multiply the cost with no latency gain inside a request. Trusted system-actor contexts (no session, no credential) and the anonymous context skip the gates; liveness is never cached.
- **D24 — Refresh is per tab, with reuse detection and fork.** Each tab owns one refresh lineage, rotated on every use; reusing a spent token revokes the whole session, and a new tab gets its own lineage by forking from a live access token. Tabs cannot share one rotating refresh token without false reuse alarms, so one lineage per tab keeps rotation and reuse detection sound while the session row stays the single revocation unit. The profile is not stored on the lineage: each refresh names it, and a switch writes nothing. See [Refresh lineages](./architecture/sessions-and-tokens.md#refresh-lineages).
- **D25 — The OIDC callback hands off a one-time code, never a token.** Refresh tokens must not land in browser history. The callback redirects with `#handoff=<code>`, a `login_handoff` challenge (60 seconds, single use) bound PKCE-style to a verifier the originating browser keeps, which the tab exchanges at `POST /v1/auth/handoff` for its tokens. See [The OIDC handoff code](./architecture/sessions-and-tokens.md#the-oidc-handoff-code).
- **D26 — Step-up is factor composition.** Step-up adds or re-verifies a factor in the current session, recomputes `acr`, sets `auth_time` to now and returns a fresh access token, so assurance is a property of the session rather than of a separate token. Self-service credential and identifier changes always require `auth_time` within `AUTH_SELF_SERVICE_MAX_AUTH_AGE` (default 10 minutes), which a just-signed-in user passes without friction, so the gate can be unconditional and `AUTH_REQUIRE_STEP_UP` no longer exists. See [Step-up](./architecture/sessions-and-tokens.md#step-up).
- **D27 — Bootstrap is one transaction behind one setup token, and the first-user hook is gone.** The single setup token is live while the operator party does not exist or OIDC is unconfirmed, so confirming OIDC first cannot destroy the token the bootstrap needs. `POST /v1/bootstrap` creates the first user, the operator party, the administrator profile with a wildcard `manage` grant and the operator party's authentication policy in one transaction, and claims the operator party with mod-core's `core_claim_operator_party`, the race-free single winner that replaced the unlocked `count(*)` check of the former first-user hook (`users.NewFirstUserHook` is deleted, with its manifest entry). The login with the bootstrap password lands on the administrator profile and the personal login does not. See [Setup-token bootstrap](./architecture/sessions-and-tokens.md#setup-token-bootstrap).
- **D28 — A person record is owned by its user, and a personal party is reached by an owned-scope grant.** The `natural_person` record a user creates for themselves (at registration, guest upgrade or `EnsurePersonalParty`) is owned by that user, not by itself, so the user's personal profile reaches its own legal record through the own arm with no extra grant and the person's party profiles and content, which the person party owns, stay out of the own arm. `EnsurePersonalParty` idempotently creates the person party and an owned-scope `manage` grant held by the personal profile over everything the person party owns (any type), never over the person record itself; the grant is invisible to the `Authorizer` until the creating transaction commits, so a caller that must authorize against it commits first.
- **D29 — Module SQLSTATE codes.** `MF101` (session invariant), `MF102` (credential invariant) and `MF103` (user invariant) are this module's own, mirroring its migration range 100 to 199 and kept distinct from mod-core's `MF001` to `MF005`; helpers live in `usersservice`. Unique violations stay `23505` with named indexes. See [Data model](#data-model).
- **D30 — The invite-only app gate runs through the engine.** The `login` gate is evaluated by the Go `Authorizer` (`Authorize(ctx-with-candidate-profile, "login", &app)`) as part of availability whenever the session's app has `invite_only`, reusing the wildcard, entity, owned-scope and actor-group arms instead of duplicating them in SQL, at the cost of one extra query only for invite-only apps.
- **D31 — Routes were replaced, not migrated.** The self-service, user-account, administrator-identity-switch, grant-admin and app-membership route families are removed in favour of `/v1/me*`, `/v1/session*`, `/v1/principals*`, `/v1/parties/{uuid}/*`, `/v1/profiles/{uuid}`, `/v1/impersonations*` and `/v1/bootstrap`, with no compatibility layer, because the identity model replaces every one of those concepts. Platform administrators are operator-party profiles plus grants; app membership is a `login` grant through mod-authz's grants API; the administrator's identity-switch token is replaced by an impersonation child session.

The decisions D1 to D4, D9 and D11 about SSH key credentials are recorded in detail in [docs/architecture/ssh-keys.md](./architecture/ssh-keys.md); D12 to D31 are recorded here only.
