# SSH Keys

## Purpose and scope

This document records the durable architectural decisions behind `mod-users`' SSH public-key capability: the `ssh_key` credential that lets a principal authenticate a git-over-SSH session against a composing application (for example `app-mfgit`/`mod-repos`). An SSH key is one credential kind of a principal, not a table of its own; see [Authentication flow](../architecture.md#authentication-flow) for how it fits alongside the module's other authentication channels, and [Principals, identifiers and credentials](../architecture.md#principals-identifiers-and-credentials) for how credentials relate to principals and profiles. Unlike the interactive kinds, an SSH key never creates a session ([Sessions and tokens](./sessions-and-tokens.md) covers those); the transport resolves the key and derives an `AuthContext` per operation.

The decisions below began in the `ssh-public-keys` plan, were carried over when SSH keys became credentials in the identity-model rewrite, and are recorded here as their durable home; code and manifest comments cite this document by its `Dn` label. Only the decisions with lasting architectural weight are covered here — schema placement, uniqueness, revocation, caching, authorization and profile derivation, and the consumer-facing Go shape. Narrower implementation detail (the accepted key-algorithm list, request/response shapes, masking rules, freshness gating) is covered in [docs/mod-users-spec.md](../mod-users-spec.md)'s Security requirements and API definition, and in [`api/openapi.yaml`](../../api/openapi.yaml).

## D1: schema placement

An SSH key is a row of `mod_users.cred_ssh_key` (key type, public key, SHA-256 fingerprint, and an `active` flag) joined one-to-one to its `mod_users.credentials` row, which carries the principal, label, expiry, optional confinement to a party and revocation. Every reference is schema-qualified.

**Rationale.** `docs-mf-standards/architecture/schema-ownership-design.md` sets the ecosystem-wide rule: a module's own tables live in `mod_<module>`, while the platform-canonical tables (`entities`, `types`, `principals`, `profiles`) stay in `public`. `mod-users` first applied the rule to the SSH-key table alone, as a deliberately mixed layout next to its older unqualified tables. The identity-model rewrite of the baseline migration then moved every `mod-users` table into `mod_users`, so the layout is no longer mixed: the rule is simply that every `mod-users` table is `mod_users.*`.

**Operational consequence.** A composing application's runtime database role needs `USAGE` on the `mod_users` schema and table privileges on the tables it uses (`SELECT` on `credentials`, `cred_ssh_key` and the tables the availability functions read to resolve keys; also writes on the credential tables and `USAGE` on their id sequences to serve the credential routes; see [Data model](../architecture.md#data-model)). The migration itself issues no `GRANT`, per `building-modules.md`'s grant conventions — the composing application's own provisioning owns that. Any backup, reset, or test-fixture tooling that enumerates "this module's tables" by scanning `public` alone will silently miss them until it is taught to look in `mod_users` too.

## D2: global uniqueness enforced in the schema

A given SSH public key resolves to **at most one active credential**, enforced by a partial unique index:

```sql
CREATE UNIQUE INDEX cred_ssh_key_active_fingerprint_uq
  ON mod_users.cred_ssh_key (fingerprint_sha256) WHERE active;
```

**Rationale.** A key must never silently authenticate as two different principals — per-principal uniqueness would let two principals register the same key and make resolution ambiguous, and the handoff that originated this capability required the ambiguity not be left to the consuming transport. The invariant is enforced **in the schema, not by a Go pre-check**, because `building-modules.md`'s grants section establishes that a module is not the sole writer of its own tables — a Go-level uniqueness check alone would lose a concurrent-registration race, letting two callers both pass the check before either commits. The `active` column mirrors `credentials.revoked_at IS NULL` and is maintained by a trigger, which is what lets a partial index express "active". The service maps the resulting Postgres `23505` unique violation to a `409 conflict` (`users.ssh_key_in_use`), identically whether the existing holder is the caller or a different principal, so the response never reveals who holds a contested key. Because the index is partial, a revoked key can be registered again later, by the same or a different principal, as a new credential with a new UUID — this index is also the resolver's lookup index (see [D4](#d4-no-cache-immediate-revocation)).

## D3: revoke, never delete

Revoking a key revokes its credential: `credentials.revoked_at` is set with a reason (`user`, `admin`, `departure`, `superseded`, `guest_upgraded` or `expired`), and the mirrored `active` flag drops. The row is never deleted. Every read and the resolver's lookup filter on `active` (and on the credential's expiry).

**Rationale.** `schema-ownership-design.md`'s deletion rule applies to every credential: a module-owned domain row that another composing application may reasonably reference — for example a credential UUID appearing in push attribution or an audit view — is retained, because no single composing app can know whether a sibling app still depends on it. This is **unlike** `mod-authz`'s grant rows, which are hard-deleted deliberately — a grant is `mod-authz`'s own internal bookkeeping that no other app's data hangs off, and a lingering revoked grant would itself be a permission-shaped record whose absence is the point. A credential row is not permission-shaped in that sense — every read and the resolver already exclude a revoked row. An SSH key is non-interactive and never a session factor, so revoking it ends no session; it takes effect on the next resolution (see D4).

## D4: no cache, immediate revocation

The resolver (`sshKeyResolver`, see [D11](#d11-resolver-consumer-contract)) issues a fresh, indexed query on every call. No process-level cache exists at any layer, and none may be added.

**Rationale.** A revoked key must stop authenticating on the very next SSH connection, not at the next token refresh — there is no token to refresh on the SSH path. A cache at any layer, even a short-lived one, would delay that by definition. The lookup also excludes a key whose credential has expired and a key whose principal entity is archived (`public.entities.archived_at IS NOT NULL`) or whose principal is disabled (`principals.disabled_at`), so archiving or disabling a principal cuts off git access immediately too, through the same mechanism. Revoking a key does **not** terminate an already-open SSH session; that is transport behavior belonging to `mod-repos`. "The next connection sees it" is the contract this module guarantees; anything about an already-open session is out of scope.

## D9: credentials operation and profile derivation

Registering, listing and revoking SSH keys on behalf of a principal is the `credentials` operation on the **principal entity**, served under `/v1/principals/{uuid}/credentials*` (list, `POST .../api-keys`, `POST .../ssh-keys`, `DELETE .../{credential_uuid}`). The `credentials` operation has `ownership_confers` true and a `max_auth_age` of 10 minutes, and `manage` implies it. The administrator routes authorize it through the `Authorizer`: a wildcard or entity grant, an owned-scope grant on the owning party, or the own arm for a personal profile whose holder owns the principal. A user manages their own keys on `/v1/me/credentials/ssh-keys` instead, authorized on the session's principal being the target. The earlier routes `/v1/user-accounts/{uuid}/ssh-keys[/{key_uuid}]` and `/v1/self/ssh-keys[/{key_uuid}]` are removed.

**Rationale.** Registering a key lets its holder authenticate over git SSH as the principal, which is credential-install authority, and the generic `update` operation also reaches every instance of a type when granted on the type entity ([architecture.md D13](../architecture.md#key-decisions)). `credentials` is its own operation so that a holder of only `update` (or `read`/`list`) on the principal, or on the `user` type entity, cannot install or revoke keys; `manage` still confers it because it implies `credentials`, as does a direct, type-level or wildcard `credentials` grant. Because the operation is `ownership_confers`, the own arm lets the owner of a service account rotate that account's key, with no special case. The ten-minute `max_auth_age` makes a stale authentication answer with the action-required `409 users.step_up_required` (the shared step-up flow of [Sessions and tokens](./sessions-and-tokens.md#step-up)); there is no separate step-up token.

**The own-principal refusal.** The administrator routes refuse a caller addressing its own principal with `403`, for every caller, service accounts included. The `/v1/principals` routes are the administration surface; a principal's own credential changes stay on `/v1/me`, which enforces the last-credential rule (the administrator door has no such check) and the `AUTH_SELF_SERVICE_MAX_AUTH_AGE` freshness gate. The ownership arm would otherwise let a principal satisfy the `credentials` operation on itself and use the administrator door to skip both. A service account cannot rotate its own keys on this door either; its keys are rotated only by its owner or an operator, who address the service account's principal, not their own. An impersonating session is refused `403 users.impersonation_not_allowed` on all four routes before the principal lookup: credential administration under another identity would let an administrator install a persistent credential for the impersonated user or for anyone the impersonated profile administers.

**Request order and existence masking.** The credential routes follow the module's error order (see [D20](../architecture.md#key-decisions)): `401` (no live session), then every stateless check (path UUIDs; the register body decoded strictly, capped at 32 KiB, with `public_key` required; the key and label format parsed by `sshkey.Parse` and `sshkey.NormalizeLabel`), then `403` (impersonating), `404` (unknown principal), `403` (the caller's own principal), `404` (a principal the caller cannot read), `403` (`credentials` refused) or `409` (a stale authentication, or a duplicate fingerprint). The key and label parse also runs at the top of the service method before authorization, so an in-process caller gets the same `400`, and a caller who may not administer the principal still sees a `400` for a malformed key. A credential that does not exist, belongs to another principal or is already revoked is a `404`, and a principal the caller may not read is indistinguishable from an unknown one ([D21](../architecture.md#key-decisions)).

**Profile derivation.** A key authenticates a principal, but a repository operation needs an acting profile. `AuthContextForOwner` derives it from the repository's owner: when the owner is a party in which the principal holds an `active` profile, that profile, provided `mod_users.credential_profile_availability` is `available` for the credential (the party's `credential_rule`, `min_acr` against the kind's base level, confinement and confirmations are evaluated with the single credential as the only factor); otherwise, if the credential is not confined to a party, the principal's personal profile, subject to the same check. A refusal is `ErrSSHKeyNotAuthorized` carrying the party's UUID. An SSH key is never an OIDC factor, so a party whose rule requires an OIDC provider always refuses it, and a party `min_acr` above the kind's base level does too. This is what keeps a key from being a way around a party's authentication policy: the same availability rules that gate an interactive session gate the key.

## D11: resolver consumer contract

`mod-repos`' SSH transport consumes key resolution through its `transport.KeyResolver` (`mod-repos/api/transport/key_resolver.go`) adapter, which wraps the two calls below. `mod-users` must not import `mod-repos`, so it exposes the Go shapes through the public facade `api/usersservice`:

- `type SSHKeyResolver` with `ResolveCredential(ctx context.Context, key gossh.PublicKey) (SSHCredential, error)` (`gossh` is `golang.org/x/crypto/ssh`, which `mod-repos`' `charm.land/ssh.PublicKey` embeds), constructed by `NewSSHKeyResolver(...)` and registered as the manifest service `sshKeyResolver`. `SSHCredential` carries the credential and principal ids and UUIDs and the id of the party the credential is confined to (zero when unconfined).
- `AuthContextForOwner(ctx context.Context, cred SSHCredential, ownerID *int64) (opctx.AuthContext, error)`, which derives the acting profile as described under [D9](#d9-credentials-operation-and-profile-derivation) and returns the `AuthContext` to install: the principal, the profile, the credential id, `ACR` equal to the kind's base level and `AuthTime` now. It performs no authorization and no writes. `usersservice.SSHKeyNotAuthorizedParty(err)` reads the party UUID off an `ErrSSHKeyNotAuthorized` refusal ("key not authorized for X").
- `var ErrUnknownSSHKey`, returned identically for an unregistered key, a revoked or expired key, and a key whose principal is archived or disabled — the resolver never distinguishes these cases to its caller. Any other error is wrapped and does **not** satisfy `errors.Is(err, ErrUnknownSSHKey)`.
- `ResolveCredential` is pre-authentication, side-effect-free, and uncached: no actor is required on `ctx` and it makes no `Authorize` call (it is a credential check, in the same category as the `POST /v1/auth/login` password check — there is no authenticated caller yet to authorize); it performs no writes of any kind, including no "last used" bookkeeping (see the consumer precondition below); and it never logs key material. `ResolveCredential` compares both the fingerprint and the canonical `authorized_keys` text of the stored key, so a stored-row mismatch can never resolve.
- A compile-time assertion (`api/usersservice/service.go`) checks `*SSHKeyResolver` against a local interface shaped like the transport's key-resolution call, so a drift in either signature fails to build rather than failing at `mfgen generate` time in a consuming application. The former `ResolveActor` method and the `SSHKeyService` it served are removed.

`sshKeyResolver` is `mod-users`' **second exported cross-module integration point**, alongside `resolveOrAnonymous` (see [Authentication flow](../architecture.md#authentication-flow)). Unlike `resolveOrAnonymous`, which a consuming module wires as HTTP middleware, `sshKeyResolver` is consumed directly as a Go value by a composing application's own transport code — no `mod-users` route calls it, and `mfgen`'s manifest resolver prunes the `provides.services` node as an unreachable root from any `mod-users` route, which is expected: the node exists to be constructed and handed to the composing application, not to be reached from this module's own HTTP surface.

**Consumer preconditions.** `ResolveCredential` runs once per *candidate* key a client offers during an SSH handshake, including unsigned RFC 4252 "query" probes that never complete authentication (`mod-repos/api/transport/publickeyauth.go`) — a genuinely unauthenticated peer can therefore trigger arbitrarily many `ResolveCredential` calls simply by opening SSH connections and offering keys. `mod-users` deliberately keeps it cheap (one indexed lookup plus the principal checks, no cache to warm, no write) so that this is inexpensive per call, but it does not itself rate-limit — that would require state and defeats the "no cache" guarantee ([D4](#d4-no-cache-immediate-revocation)) that makes revocation immediate. The composing transport (`mod-repos`, composed by `app-mfgit`) is therefore responsible for **rate-limiting SSH handshakes and capping the number of candidate keys accepted per connection** at the transport layer, before or alongside calling `ResolveCredential`. This is a precondition on `sshKeyResolver`'s consumers, not something `mod-users` enforces.
